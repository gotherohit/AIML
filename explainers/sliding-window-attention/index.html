Sliding window attention: why 22 of Gemma 3's 26 layers can't see past 512 tokens

A sliding window layer only looks at the last W tokens, so its memory stops growing. Stacking layers extends the reach on paper, but a real test on Gemma 3 shows why models still keep a few full-attention layers.

In one line: a sliding window layer only looks at the last W tokens, so its memory stops growing; stacking layers lets information travel further on paper, but in practice models keep a few full-attention layers for the long view.

1 · Full attention (the normal way)

Quick refresher. In every layer, each token makes three vectors: a query ("what am I looking for?"), a key ("what do I contain?") and a value ("what I pass on"). Attention compares a token's query with the keys of itself and every earlier token (one comparison each), turns the scores into weights, and mixes the values. To avoid recomputing keys and values, the model stores them, in every layer: the KV cache. Memory grows linearly: double the chat, double the cache.

Why "quadratic" if only the last token is predicting?

It's true that when the model writes a new token, only that one new query is compared against the stored keys. That's N comparisons for one token when N tokens are in the cache: linear. The quadratic part comes from adding up all the tokens:

Reading your prompt (prefill). All N prompt tokens are processed at once, and each one compares itself with every token before it. Token 1 does 1 comparison, token 2 does 2, ... token N does N. Total: 1 + 2 + ... + N = N × (N + 1) / 2.
1,000 tokens → 500,500 comparisons. 2,000 tokens → 2,001,000. Double the length, about 4× the work. That's what quadratic means.
Writing the answer (decode). Each new token is one query against everything so far, so every token costs a little more than the one before: token 1,001 does 1,001 comparisons, token 2,000 does 2,000. Writing tokens 1,001 to 2,000 costs about 1.5 million in total. One step is linear; the whole sequence adds up to quadratic again. (The KV cache is what keeps each step down to one query. Without it, every step would redo the whole prompt.)
With a 512-token window, no token ever does more than 512 comparisons. After the first 512 tokens, every token costs the same, so the total grows in a straight line: double the length, about double the work.

One honest detail: attention is only part of a layer. The feed-forward part costs the same for every token whatever the length, so on short prompts most of the compute isn't attention at all. The quadratic part takes over as texts get long. Mistral's paper says the "number of operations in vanilla attention is quadratic in the sequence length" (attention, not the whole model).

2 · The window

A sliding window layer changes one rule: a token may only look at the last W tokens (itself included). Older tokens get exactly zero attention in that layer, so their keys and values are never needed again and can be dropped. The cache for that layer stops at W tokens however long the text gets. Mistral calls this a rolling buffer: position i is stored in slot i mod W, overwriting the oldest.

3 · Real model: Gemma 3 1B

From its config: 26 layers, window 512 tokens. Layers 6, 12, 18, 24 are full attention (blue), the other 22 are window layers (yellow): 5 window, 1 full, repeated.

Paper vs config: checked

The Gemma 3 paper says local layers get "a smaller span of only 1024 tokens", but the 1B config says 512. I checked Google's own reference code (github.com/google/gemma_pytorch, gemma/config.py):

Conclusion: there's no conflict. The paper's 1,024 is the window of the 4B, 12B and 27B models; Google's code gives the 1B a 512 window, and the demo config matches Google's code on every field above. So whenever a window size appears on this page, the model size is named with it.

What "a 512 window" means exactly: Google's code masks a key when it's 512 or more positions back, so a token sees itself plus the 511 before it: 512 in total. The demo measured exactly that (512 tokens with nonzero attention), and the cache keeps 511 because the next token brings itself.

Not cross-checked: my test uses Unsloth's public re-upload, because Google's Hugging Face repo needs a login. Its config matches Google's code; the weights couldn't be compared byte for byte. The 270M second check isn't in Google's reference code, so its config is taken from the re-upload only.

6 · Reach on paper

The key fact: a layer's output for a token isn't just that token any more. It's a mix of everything the token looked at. The next layer then looks at those mixes, so it gets information second-hand.

Tiny example: a window of 3 (a token sees itself and the 2 before it), 9 tokens, and we follow token 9:

LayerToken 9 looks at…which already containSo token 9 now carries
1tokens 7, 8, 9just themselves7 to 9
2layer-1 mixes of 7, 8, 9mix of 7 holds 5, 6, 75 to 9
3layer-2 mixes of 7, 8, 9mix of 7 holds 3 to 73 to 9
4layer-3 mixes of 7, 8, 9mix of 7 holds 1 to 71 to 9

Every layer, token 9 reaches 2 more tokens back. No single layer ever looked further than 2 back, yet after 4 layers token 1 can influence token 9. It's like a message passed down a row of people who can each only talk to their neighbours.

Real numbers. In Gemma 3 1B (window 512 = itself + 511 before), token 2,000 sees tokens 1,489 to 2,000 in layer 1. Token 1,489's own mix already holds tokens back to 978, so in layer 2 token 2,000 carries information from 978 onwards, and so on, 511 more per layer. Over 26 layers that's 26 × 511 = 13,286 tokens; people usually round it to layers × window = 13,312. The video rounds it to "over 13,000", which is true either way.

Mistral's paper describes this exactly: "after k attention layers, information can move forward by up to k × W tokens"; with W = 4,096 and 32 layers, a "theoretical attention span of approximately 131K tokens". (Mistral defines the window as the 4,096 positions before the token, so its hop is a full W.)

Why "on paper". This only says a path exists. It's an upper limit, not a promise. To bring a fact from token 1 to token 2,000, every hop along the way has to choose to carry it forward, while each hop is also mixing hundreds of other tokens. Whether a trained model really does that is a separate question, and section 7 tests it.

7 · Real run: the recall test

Every prompt is about 1,530 tokens: plain filler text, then "Remember this: the secret code is 7294.", then more filler, then "Now answer. The secret code is". Only the position of the code sentence changes. Greedy decoding, 5 tokens. Each prompt runs twice: the normal model, and the model with its 4 full layers limited to the same 512-token window (the 22 window layers unchanged). Because every prompt is longer than the window, the edit is active in every run, including the inside-the-window control. Distance = tokens from the end of the code sentence to the end of the prompt.

How the limit works. Attention has a mask: before the scores become weights, every position a token isn't allowed to see gets a huge negative number, which turns into a weight of exactly 0. Causal masking (no peeking at future tokens) works this way, and so does the window: a window layer is a normal attention layer whose mask also blocks keys 512 or more positions back. The library lets you pass one mask for the window layers and one for the full layers. For the "limited" runs I passed the window mask to the full layers too. Nothing else changed: same weights, same RoPE base (1,000,000) in those layers, same prompt.

Checked (1,681-token prompt, last token): full layers give nonzero attention to 1,681 tokens normally and 512 when limited; window layers give 512 both ways. And the "normal" runs, which pass masks explicitly, give exactly the same output as running the model with no mask argument at all (largest difference in the logits: 0).

What this does and doesn't show. It shows that in this model, recall beyond the window goes through the full layers: take their long view away and the "13,312 tokens on paper" doesn't help. The control (code inside the window, same prompt length) shows the edited model still works: 6 of 6 right. The drop to 0 of 9 happens exactly when the code leaves the window. It does not show what a model trained with only window layers can do; Gemma was trained with its full layers, and the video says so too. DeepSeek's V4.1 Flash paper cites research (Chen et al., 2025) finding the effective reach of sliding windows "much smaller than the theoretical".

Second check: Gemma 3 270M

Same test on the smaller model (18 layers, 3 full). Normal: 15 of 15. Full layers limited, code inside the window: 4 of 6 (it always answered with a number, but got 3815 wrong twice: "4815" and "4015"). Beyond the window: 0 of 9, every answer "the the the the the". Gemma 3's paper: moving from 1:1 to 5:1 had "minimal impact on perplexity", and the window "can be reduced significantly without impacting perplexity".

9 · Why it matters: memory

Gemma 3's paper, a 2B model at a 32k-token context: "global only" attention gives a 60% memory overhead on top of the model; with 1,024-token windows it drops to less than 15%.

RoPE link: Gemma 3 uses RoPE base 1,000,000 for full layers and 10,000 for window layers (paper §5.3, and the config's rope_theta / rope_local_base_freq).
