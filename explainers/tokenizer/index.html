Part 1. The problem

What a model can read, and why text has to be cut up at all.

GPT-4o's tokenizer is called o200k_base. OpenAI's own library (tiktoken) lists it for GPT-4o, GPT-4.1, GPT-5, o1, o3 and o4-mini. This article says "GPT-4o" rather than "ChatGPT" because the tokenizer of the newest ChatGPT model is not published.

The model never sees the letters. It sees a list of numbers, one per token. The program that cuts text into tokens and gives each one its number is the tokenizer. The rest of this page is about how that program is made and why it gives these results.

2. Computers already store text as numbers

Start at the very bottom. A computer only stores numbers. For text there is a world-wide agreement called Unicode: every character in every language has a fixed number (its code point), written like U+0068 for "h".

To save it in a file, each code point is written as 1 to 4 bytes using a scheme called UTF-8. A byte is a small number from 0 to 255 (8 bits: 28 = 256 possible values).

Important for later: any text at all can be written with only 256 different byte values. That is why modern tokenizers start from bytes.

2b. How UTF-8 turns a number into bytes (and back)

How does a code point like "U+20B9" relate to the bytes in a file? Short answer: only bytes are stored. "U+20B9" is never written in the file; it is just how people write the character's number. UTF-8 is the rule that turns that number into bytes, and back.

1. What "U+" and hexadecimal mean

Normal counting is base 10: digits 0–9, and each position is worth 10× the one to its right (1, 10, 100…). So 104 = 1×100 + 0×10 + 4×1.

Hexadecimal is base 16: it needs 16 digits, so after 9 it uses letters:

The letter h is number 104. 104 = 6 sixteens + 8 ones, so in hex it is 68. Unicode pads it to 4 digits and puts "U+" in front: U+0068. "U+" only means "this is a Unicode number, written in hex".

Total: 8,377. U+20B9 and 8,377 are the same number written two ways. People like hex because each hex digit is exactly 4 switches (bits), which makes the next part tidy.

Each switch has a fixed worth: 128, 64, 32, 16, 8, 4, 2, 1. The byte's value is the sum of the switches that are on (1). All on is the biggest: 255.

3. The first switches of each byte are a label

UTF-8 uses the first few switches of every byte as a label. The rule: count the 1s before the first 0. That is how many bytes the character has. A byte starting with 10 is a continuation byte.

The value ranges are not extra rules; they come straight from the labels. Every byte that starts with 1110 lies between 11100000 = 224 and 11101111 = 239.

Strictly, 192, 193 and 245–247 never appear in valid UTF-8: they would only encode numbers that fit in fewer bytes, or numbers past Unicode's last character (U+10FFFF). The label idea is what matters.

4. The template: pour the number into the free switches

After the label, the remaining switches of each byte are empty slots, and the character's number is poured into them, in order.

₹ is 8,377. In switches that is 16 bits: 0010000010111001. A 3-byte character has exactly 16 free slots: 1110____ (4) + 10______ (6) + 10______ (6). Pour the bits in, 4 then 6 then 6 (orange = label, blue = the number):

So ₹ is stored as the three bytes 226 130 185, and nothing else.

Why 3 bytes and not 2? A 2-byte character has only 5 + 6 = 11 free slots, enough for numbers up to 2,047. ₹ (8,377) needs more, so it takes the 3-byte form (16 slots, up to 65,535). Most emoji are bigger still and take 4 bytes.

5. Reading it back

  1. The program reads 226. Label 1110: this character is 3 bytes.
  2. It checks the next two bytes (130, 185) start with 10. They do, so they belong to this character.
  3. It removes the labels and glues the leftover switches: 0010 + 000010 + 111001 = 8,377.
  4. It looks up 8,377 in the Unicode table: ₹.
Picture a train. The first carriage carries a sign: "this train has 3 carriages" (label 1110). Every other carriage carries a sign: "I belong to the train in front" (label 10). The passengers in the free seats are the pieces of the number.

6. The bytes do not say which rule to use

A file does not carry a label saying "I am UTF-8"; the program has to be told or assume it. Read the same three bytes 226 130 185 with the old Windows-1252 rule (one byte = one character) and you get â‚¹: byte 226 becomes â, 130 becomes ‚ (a low quote mark), 185 becomes ¹. That is the garbled text you sometimes see on websites.

Why this matters for tokenizers: byte-level BPE works on these stored bytes, not on characters. A token can hold the first carriage without the ones behind it. That is why some tokens are half a character (the emoji pieces in section 11) and only make sense once joined with the next tokens.

3. What a language model needs from us

A language model does one job again and again: look at the pieces so far and give a score to every possible next piece, then pick one. That one fact forces two things:

  1. A fixed, finite list of pieces. The model's last step produces one score per entry of the list, so the list has to be decided before the model is built. This list is the vocabulary.
  2. Each piece has a position number in that list (its ID). Inside the model, ID k picks row k of a big table of learned numbers (the embedding table). That row is what the model actually works with.

Real example, the small open model SmolLM-135M: its list has 49,152 entries and each row has 576 numbers, so the table holds 28,311,552 numbers. That is 21% of the whole model (134,515,008 numbers). In this model the same table is used both to read the input and to score the next piece (config: tie_word_embeddings = True).

So the tokenizer must turn any text into IDs from a fixed list, and turn IDs back into the exact same text. Everything that follows is about how to choose that list.

4. Three ways to cut text

There are three obvious choices for "a piece" (the first comes in two versions). I measured them all on the same 5,166,860 bytes of new children's stories (text the tokenizer never saw):

"Pieces needed" = how many IDs the model would receive for this text. "Size of the list" = how many different entries the list must contain.

Option A1: one piece per character

Each character (h, e, ₹, “, 🙂...) is one piece, so the text needs 5,164,777 pieces, one per character. The problem is the list: it must have an entry for every character that could ever appear. This one text uses only 79 different characters, but Unicode has well over 150,000, and any character missing from the list could not be written at all.

Option A2: one piece per byte

Here a piece is one byte, not one character. Every character is first written as its 1 to 4 bytes (section 2), and each byte becomes its own piece. So the pieces needed = the number of bytes in the text, 5,166,860, slightly more than the 5,164,777 characters, because 1,042 characters in this text take more than 1 byte. The most common one is the curly quote “, which is the 3 bytes 226 128 156 and so becomes 3 pieces:

226128156

Plain letters like h are 1 byte, so they are still 1 piece each.

The gain: the list needs only 256 entries. That 256 is not a number of characters; it is the number of different values one byte can hold (8 switches = 2×2×2×2×2×2×2×2 = 256). Every character in every language is written with these same 256 values (several of them in a row for bigger characters), so a list of 256 can write any text and nothing is ever missing.

The cost: the text gets long, one ID per byte. The model has to work through 5,166,860 steps instead of about 1,233,789 with GPT-4o's tokenizer, and spends effort on spelling instead of meaning. The GPT-2 paper notes that byte-level models "are not competitive with word-level" ones on large datasets.

Option B: whole words

Short sequences, but the list never ends. I built a word list from the 22,161,827 characters of training stories: 11,336 different words (2,740 of them seen only once). Then I checked new text against it:

But in the BPE paper's own text, 43% of the words are missing: "translation", "vocabulary", "subword", "segmentation". A word-level model simply cannot write a word that is not on its list. Real tokenizers would also need separate entries for every "dog", "dogs", "Dog", typo and name.

The middle road: frequent words become one piece, rare words are spelled from smaller pieces, and in the worst case single bytes, so nothing is ever missing. Our own small tokenizer from Part 2 cuts those "missing" words like this:

Part 2. Training a tokenizer

Where the list comes from.

5. What does "training a tokenizer" mean?

Short answer: it is not like training an LLM. The word "training" only means the list is learned from example text instead of being written by hand. There is no neural network, no GPU and no guessing. It is counting.

The three things a person chooses before training

  1. The example text. A big sample of the kind of text the model will see later. (Ours: 22,161,827 characters of TinyStories, a public set of simple children's stories.) If the sample has little code, or little of some language, those get few list entries and are cut into many small pieces later.
  2. The step-0 rule: how text is chopped into word-sized chunks before counting (section 6).
  3. How many merges, which sets the final list size. The BPE paper calls this "the only hyperparameter of the algorithm". GPT-2 used exactly 50,000 merges: 256 bytes + 50,000 merges + 1 special marker = 50,257 entries.

  • Glued and New piece: which two pieces were joined, and the piece that came out.
  • Its ID: the new piece's token number. It starts at 256, not 1, because IDs 0 to 255 are already taken by the 256 single bytes (section 7). So merge 1 gets ID 256, merge 2 gets 257, and so on: ID = 255 + merge number.

In the file itself each rule is one line of text, for example: 1 ' ' 't' ' t' 641902

Why the tokenizer is then frozen forever

The model's row number k is learned for whatever piece has ID k. If you changed the list after training the model, every row would suddenly belong to a different piece and the model would read nonsense. So a model and its tokenizer are a fixed pair. The glitch-token paper (Land & Bartolo 2024) is about what goes wrong because the two are made separately: "the disconnect between tokenizer creation and model training".

Order of events: 1. collect text → 2. train the tokenizer (counting, minutes to hours) → 3. freeze it → 4. turn all training text into IDs → 5. train the LLM on those IDs (the expensive part).

6. Step 0 in detail: chopping text into chunks before training

Before any counting, the text is cut into word-sized chunks by a fixed, hand-written rule. Merges are only ever counted inside a chunk, never across two chunks. Apart from the special tokens (section 12), this rule is the only part of a tokenizer that a person writes by hand; everything else is learned.

6a. Why bother? Experiment

To see what step 0 does, I trained three small test tokenizers of my own, not real GPT-2. To keep it quick each one learned only 500 merges from the same 300,000 characters. (The real GPT-2 tokenizer has 50,000 merges; a small test is enough to show the effect.) The only difference between the three is the step-0 rule: none at all, splitting at spaces only, or GPT-2's chopping rule, the pattern GPT-2 uses before merging. Then I used each one on 100,000 characters of new text:

"Glued across words" = a learned piece that contains a space in the middle, or ends in a letter followed by a space. "Letters glued to punctuation" = a piece mixing letters with punctuation, like day.

Examples of pieces learned with no step 0: Once·upon·a·time,·there·was·a· Once·upon·a·time,· One·day,·a· .·One·day,· One·day,· said,·" ·and· the·

Examples with spaces only: Lily. day, day. friends. fun. happy. ily. ing.

Without step 0 the list fills with pieces that are really bits of phrases (one entry for "Once·upon·a·time,·there·was·a·"). With spaces only, words come in many copies glued to punctuation. The GPT-2 paper describes exactly this: BPE "including many versions of common words like dog since they occur in many variations such as dog. dog! dog?", which wastes list entries. With GPT-2's chopping rule, the test tokenizer's 500 entries go to cleaner, reusable pieces instead.

Notice the raw token count on new text is not the point here: the no-step-0 version can even use fewer tokens on stories, because it memorises common phrases of this one kind of text. The cost: a list full of entries that only make sense for this one kind of text, and pieces that do not line up with words.

6b. The second reason: speed

Training happens in two stages:

  1. Once, at the start: one pass over the whole text. Cut it into chunks (step 0) and count how often each different chunk appears. The result is a dictionary of chunk → count. Our 5,411,109 chunks become only 13,119 different ones, because the same words repeat. The most common: . 421,616 times, , 235,432 times, ·the 211,031 times, ·and 196,057 times.
  2. Every merge round after that (8,000 rounds for our tokenizer) works only on the dictionary. To count pairs, it looks at each of the 13,119 entries once and adds its pairs count times. To glue the winning pair, it again only changes the 13,119 entries.

Why this saves time. Take one chunk, ·the, which appears 211,031 times. In every round the program must count the pairs inside it (·t+he and so on).

  • Without the dictionary it would read ·the 211,031 separate times and add 1 each time.
  • With the dictionary it reads ·the once and adds 211,031 in one go. Same answer, one look instead of 211,031.

The same happens for every chunk, in every round. Over the whole text, the first round reads:

Without the dictionaryWith the dictionary
What is readevery copy of every chunkeach different chunk once

And this repeats in all 8,000 rounds, which is why the dictionary matters so much.

The BPE paper does exactly this: "the algorithm can thus be run on the dictionary extracted from a text, with each word being weighted by its frequency". It only works because of step 0: merges never cross chunks, so two copies of the same chunk always change in exactly the same way, and one entry with a count can stand for all of them.

6d. Why is the space glued to the front of the word?

In normal text almost every word comes right after a space. Keeping that space with the word means "·the" is one very common chunk, and the space itself costs nothing extra. It also marks "a new word starts here", so the model can tell ·hello (a word on its own) from hello at the start of a message or glued to something. GPT-2's paper says allowing spaces into word chunks "significantly improves the compression efficiency". The price: the same word gets two entries, with and without the space. That is exactly the hello puzzle from section 1.

Same sentence, step 0 of GPT-4 (cl100k_base):

  • GPT-4o keeps I'm and dog's as one chunk, and splits words at capital letters: SolidGoldMagikarp → Solid | Gold | Magikarp, before any merge happens.
  • Line breaks and indentation get their own rules (useful for code).

6f. The other style: SentencePiece and "▁"

Google's SentencePiece toolkit works differently: its paper describes replacing every space with a visible marker "▁" (U+2581) and treating the text as one stream, so the space marker is simply part of the pieces. Gemma's list uses this marker: ▁hello. In the Hugging Face files of GPT-style tokenizers (Qwen, Llama) you will see "Ġhello": Ġ is only how those files print a space byte. Same idea, different printing.

Step 0 decides where pieces are allowed to form. BPE then decides which pieces form, purely by counting.

7. Step 1: start from the 256 bytes

The starting list is the 256 possible byte values. Every chunk is written as its bytes: ·hello = 32 104 101 108 108 111.

Why bytes and not "all characters"? The GPT-2 paper: covering all of Unicode as single symbols would need "a base vocabulary of over 130,000 before any multi-symbol tokens are added", while "a byte-level version of BPE only requires a base vocabulary of size 256". And because every possible text is bytes, no input can ever be impossible to write.

What happens to a character that is 3 bytes?

BPE never sees characters, only byte numbers. So at the start, a 3-byte character is simply 3 separate pieces. Take the curly quote “, which is the bytes 226 128 156:

Gemma's different design: characters first, bytes only as a backup ("byte fallback")

GPT-style tokenizers (GPT-2, GPT-4o, Llama, Qwen) always start from bytes: every text is bytes, and pieces are built by gluing bytes. 8. Steps 2 and 3: count, glue, repeat

Why is it called "Byte Pair Encoding"?

The name is older than AI. BPE started in 1994 as a way to compress files (Philip Gage, "A New Algorithm for Data Compression", C Users Journal). The BPE paper describes the original as "a simple data compression technique that iteratively replaces the most frequent pair of bytes in a sequence with a single, unused byte". So the name says exactly what it did: look at pairs of bytes side by side, and re-encode the file by replacing the most common pair with one new byte, making it shorter.

Example: a file whose bytes are ABCABCABD (9 bytes). Each step replaces the most common pair with a byte the file never uses:

StepMost common pairSeenReplace withBytes after
1AB3 timesZZCZCZD(6)
2ZC2 timesYYYZD(4)

9 bytes became 4, plus a small table (Z = AB, Y = ZC) to unpack it: replace in reverse order (Y becomes ZC → Z becomes AB) and you get back exactly ABCABCABD.

In 2016 Sennrich and colleagues borrowed the same loop for language: glue the most frequent pair of characters to build a list of word pieces. The name stayed even though they worked on characters; the GPT-2 paper remarks that "despite its name, reference BPE implementations often operate on Unicode code points and not byte sequences". GPT-2 went back to real bytes, which is the version on this page.

One difference: Gage could only use byte values the file did not already contain, and there are only 256. A tokenizer has no such limit: each merge simply gets the next new ID (256, 257, 258…), so the list can grow to 50,000 or 200,000 entries.

The training loop

The whole training loop:

  1. Look inside every chunk and count every pair of neighbouring pieces (each chunk counts as many times as it appears in the text).
  2. Take the pair with the highest count. Give the glued pair a new ID (the next free number) and add it to the list. Write down the rule.
  3. Everywhere that pair appears, replace it with the new piece.
  4. Go back to 1. Stop when the list reaches the chosen size.

Each round adds exactly one entry. Pieces can grow by gluing two already-glued pieces (" t" + "he" → " the"). Ties are broken by a fixed rule so the result is repeatable.

10. Encoding: turning your text into IDs

When you send a message, the tokenizer does not search for the longest matching word. It replays the training:

  1. Step 0 with the same rule: cut into chunks.

11. Decoding: turning IDs back into text

The reverse is simple: look up each ID's bytes, join all the bytes, read them as UTF-8. For IDs that came from encoding real text you always get back exactly the text you started with.

One catch: a single piece can be half a character. GPT-4o writes the face-palm emoji (13 bytes) as 5 tokens:

<20·f0·9f·a4>93,643<a6>99‍2,524♂178,729️15,148

The first and some middle pieces are just fragments of the emoji's bytes. Alone they are not valid text; only together do they decode to 🤦‍♂️. (This is also why one emoji can cost several tokens: GPT-4 uses 8 for it.)

The decoding chain, step by step

When a model produces token IDs, this is what turns them into text. Example: GPT-2 writes the curly quote “ as two tokens, IDs 447 + 250.

  1. Look up each ID's bytes in the tokenizer's list. A piece can be any number of bytes, not always a pair: ID 447 = bytes 226 128 (half a character), ID 250 = byte 156. "h" is 1 byte, "·hello" is 6.
  2. Join all the bytes into one row: 226 128 156.
  3. The UTF-8 reader walks along the row using the labels (section 2b): a byte starting with 0 is a character on its own; 110 means "me plus 1 more byte"; 1110 means "me plus 2 more" (226 is 1110 0010); every following byte must start with 10. Here 128 and 156 both do, so the three bytes give “.

What if the model picks a token that does not finish the character?

It can happen. The model picks one token at a time, and nothing inside it forces the bytes to fit together. Three things deal with it:

1. Usually the model continues correctly. In its training text the piece 226 128 was always followed by the rest of a character (156, 157, 153…), never by a letter, so it learns that very strongly. A wrong pick is rare, but not impossible.

2. If it happens, the decoder does not crash; it shows a replacement mark. Tested with GPT-2's real decoder (OpenAI's tiktoken):

Token IDsBytesDecoded text
447 + 250 (correct)226 128156“
447 + 71 (half piece, then h)226 128104�h
447 (half piece alone)226 128�
447 + 251 (half piece, then 157)226 128157”

Byte 104 ("h") starts with 0, not 10, so the reader knows the character was broken. It writes � (the official Unicode "replacement character") in place of the broken bytes and carries on normally with h. tiktoken does this by default (its decode has errors="replace", the same setting as minibpe.py in Part 6). In strict mode it stops with an error instead: 'utf-8' codec can't decode bytes in position 0-1: invalid continuation byte.

3. A different wrong pick can give a valid but different character. If the model picks byte 157 instead of 156 after 226 128, the bytes fit perfectly and you get ” instead of “. No error at all: that is just an ordinary wrong prediction, like picking the wrong word.

While text streams in word by word, a program showing it receives the half piece 226 128 first. It cannot print anything yet, so it waits for the next token to finish the character. That is why a well-built chat app does not flash half a character; at worst you would see � if the model really did go wrong.

The trade-off:

  • Bigger list → more words are one piece → shorter inputs (our curve in section 8), so more text fits in the model's context and each request is cheaper and faster.
  • But every entry needs its own row of learned numbers (in SmolLM-135M the table is already 21% of the model), and the model must score every entry at every step.
  • Rare entries are seen only a few times during model training, so their rows stay poorly trained. The extreme case is the glitch token (section 17).
Part 5. Consequences

Odd behaviour that comes straight from the tokenizer.

15. Numbers

How "1234567" is cut: GPT-2 123 | 45 | 67; GPT-4 and GPT-4o 123 | 456 | 7 (their step 0 allows at most 3 digits, grouped from the left); Qwen2.5 and Gemma 3 one digit per token (the Gemma 3 report lists "split digits" as a design choice of its tokenizer). " 2024" is one token in GPT-2 but "202" + "4" in GPT-4.

Research: Singh & Strouse 2024 tested GPT-3.5 and GPT-4 on arithmetic and found that grouping digits from the right (forced by writing numbers with commas, 1,234,567) "leads to largely improved performance", and the errors with left-to-right grouping follow fixed patterns. They also note LLaMa and PaLM chose single-digit tokens.

16. Other languages

The list is learned from example text, so languages that were rare in that text get few entries and are cut into many small pieces. Petrov et al. 2023 measured the same text translated into many languages: tokenized lengths differ "up to 15 times in some cases", and even byte-level models show "over 4 times the difference" for some pairs. That means higher cost, slower answers and less room in the context window for those users.

17. Glitch tokens

"·SolidGoldMagikarp" is a single entry in GPT-2's list (so it was frequent in the text the tokenizer was trained on), but almost never appeared in the text the model was trained on. So its row was barely trained. The paper says such inputs can "induce unwanted model behaviour". Land & Bartolo 2024 define these as "tokens present in the tokenizer vocabulary but that are nearly or entirely absent during model training" and found them across many models. In GPT-4 and GPT-4o the same string is 5 pieces (GPT-4o's step 0 already cuts it at the capital letters).

18. Other recipes

  • BPE (Sennrich et al. 2016, from a 1994 compression trick): start small, glue the most frequent pair. Used by GPT, Llama, Qwen, Gemma.
  • WordPiece: used by BERT (2018) with a 30,000-token list. Also builds pieces of words; how it picks them differs from BPE.
  • Unigram (Kudo 2018): the opposite direction. Start with a "reasonably big seed vocabulary", then repeatedly remove the pieces whose removal hurts the least, keeping the top 80% each round, until the target size; single characters are always kept so nothing is missing.
  • SentencePiece (Kudo & Richardson 2018): a toolkit, not a fourth algorithm. It can train BPE or Unigram directly on raw text, with the "▁" space marker.

19. Cost and context limits

API prices and context windows are counted in tokens, not words or characters. So everything above (the list size, step 0, the language, emoji, how numbers are cut) changes how much a request costs and how much text fits.

20. The complete code

This is a full byte-level BPE tokenizer in one file, about 200 lines including explanations, following exactly the recipe of Parts 2 and 3. It can train on any text file, encode, decode, handle special tokens, and save and load itself. It is the same algorithm I used for every number on this page, and the tests in section 25 check that it reproduces them exactly.

You need: Python 3.8 or newer, and one extra package: pip install regex. (Python's built-in re does not understand \p{L}, "any letter in any language", which the GPT-2 step-0 pattern uses.)

Save it as minibpe.py, or download the files: minibpe.py · test_minibpe.py · README

r"""
minibpe.py - a complete byte-level BPE tokenizer in one file.

It uses the same recipe as GPT-2's tokenizer:
  step 0: cut the text into word-sized chunks with a fixed pattern (a space stays on the front of a word)
  step 1: write every chunk as its UTF-8 bytes (256 possible values = the starting list)
  step 2: count every pair of neighbouring pieces, glue the most frequent pair into a new piece
  step 3: repeat until the list has the size you asked for

What you need:
  Python 3.8 or newer
  the "regex" package (pip install regex). Python's built-in "re" module does not understand
  \p{L} ("any letter in any language"), which the GPT-2 pattern needs.

Try it:
  python minibpe.py                      train on a small built-in sample
  python minibpe.py my_text.txt 1000     train on your own text file, list size 1000
"""

import json
import sys
from collections import Counter

import regex

# Step 0 pattern, copied from GPT-2 (OpenAI's tiktoken library, "gpt2" encoding).
# Read it as "try these alternatives, left to right":
#   '(?:[sdmt]|ll|ve|re)   English endings after an apostrophe: 's 't 're 've 'm 'll 'd
#    ?\p{L}+               an optional space, then one or more letters        ( hello)
#    ?\p{N}+               an optional space, then one or more digits         ( 2024)
#    ?[^\s\p{L}\p{N}]+     an optional space, then other symbols              ( !!)
#   \s+(?!\S)              a run of spaces, leaving the last one for the next word
#   \s+                    any other run of spaces / new lines
GPT2_SPLIT_PATTERN = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""


def count_pairs(ids, counts, weight=1):
    """Add every neighbouring pair in the list `ids` to the Counter `counts`.

    Example: ids = [104, 101, 108, 108, 111]  ("hello")
    pairs:   (104,101) (101,108) (108,108) (108,111), each counted `weight` times.
    """
    for pair in zip(ids, ids[1:]):
        counts[pair] += weight


def merge_pair(ids, pair, new_id):
    """Return a new list where every occurrence of `pair` side by side is replaced by `new_id`.

    Example: merge_pair([104, 101, 108, 108, 111], (108, 108), 300)  ->  [104, 101, 300, 111]
    """
    out = []
    i = 0
    while i < len(ids):
        if i + 1 < len(ids) and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            out.append(new_id)   # found the pair: write the new piece, skip both
            i += 2
        else:
            out.append(ids[i])   # not the pair: copy this piece unchanged
            i += 1
    return out


class Tokenizer:
    """Holds what a tokenizer knows, and the four things it can do: train, encode, decode, save/load."""

    def __init__(self, pattern=GPT2_SPLIT_PATTERN):
        self.pattern = pattern
        self.splitter = regex.compile(pattern)
        # merges: (left id, right id) -> new id. Python dicts remember insertion order,
        # so this is also the order in which the merges were learned.
        self.merges = {}
        # vocab: id -> the bytes that piece stands for. It starts with the 256 single bytes.
        self.vocab = {i: bytes([i]) for i in range(256)}
        # special tokens: name -> id, e.g. "<|endoftext|>" -> 1000. Added by hand, never learned.
        self.special = {}

    # ------------------------------------------------------------------ training
    def train(self, text, vocab_size, verbose=False):
        """Learn (vocab_size - 256) merges from `text`."""
        if vocab_size < 256:
            raise ValueError("vocab_size must be at least 256 (the single bytes)")
        if self.merges:
            raise ValueError("this tokenizer is already trained; make a new Tokenizer()")

        # Step 0: cut into chunks, and count how often each different chunk appears.
        # Most chunks repeat (" the" appears thousands of times), so we keep each different
        # chunk once together with its count. Much less work than looking at every copy.
        chunk_counts = Counter(self.splitter.findall(text))

        # Step 1: every chunk becomes its list of byte values.
        words = [[list(chunk.encode("utf-8")), count] for chunk, count in chunk_counts.items()]

        for step in range(vocab_size - 256):
            # Step 2a: count every neighbouring pair inside every chunk.
            pair_counts = Counter()
            for ids, count in words:
                count_pairs(ids, pair_counts, count)
            if not pair_counts:
                break  # every chunk is already a single piece: nothing left to merge

            # Step 2b: the most frequent pair wins. If two pairs tie, the one with the smaller
            # ids wins, so training always gives the same result for the same text.
            best = max(pair_counts, key=lambda p: (pair_counts[p], -p[0], -p[1]))
            new_id = 256 + step

            # Step 2c: glue the winner everywhere, and remember the rule.
            for word in words:
                word[0] = merge_pair(word[0], best, new_id)
            self.merges[best] = new_id
            self.vocab[new_id] = self.vocab[best[0]] + self.vocab[best[1]]

            if verbose:
                print("merge %d: %r + %r -> %r  (seen %d times)" % (
                    step + 1, self.piece(best[0]), self.piece(best[1]), self.piece(new_id), pair_counts[best]))

    def add_special_tokens(self, names):
        """Give hand-made marker tokens the next free ids. Call this after train()."""
        for name in names:
            if name not in self.special:
                self.special[name] = len(self.vocab) + len(self.special)

    # ------------------------------------------------------------------ encoding
    def _encode_chunk(self, chunk_bytes):
        """Turn one chunk's bytes into ids by replaying the learned merges, earliest first."""
        ids = list(chunk_bytes)
        while len(ids) >= 2:
            # Of all neighbouring pairs, find the one whose merge was learned earliest
            # (smallest new id). Pairs with no merge get "infinity", so they never win.
            pair = min(zip(ids, ids[1:]), key=lambda p: self.merges.get(p, float("inf")))
            if pair not in self.merges:
                break  # no neighbouring pair has a rule: we are done
            ids = merge_pair(ids, pair, self.merges[pair])
        return ids

    def encode(self, text, allow_special=True):
        """Text -> list of ids."""
        ids = []
        if allow_special and self.special:
            # Cut the text around the special tokens first, so "<|endoftext|>" becomes one id
            # instead of being spelled out as < | e n d ...
            names = sorted(self.special, key=len, reverse=True)
            parts = regex.split("(" + "|".join(regex.escape(n) for n in names) + ")", text)
        else:
            parts = [text]
        for part in parts:
            if part in self.special and allow_special:
                ids.append(self.special[part])
                continue
            for chunk in self.splitter.findall(part):
                ids.extend(self._encode_chunk(chunk.encode("utf-8")))
        return ids

    # ------------------------------------------------------------------ decoding
    def decode(self, ids):
        """List of ids -> text. Join every piece's bytes, then read them as UTF-8."""
        special_by_id = {i: name for name, i in self.special.items()}
        data = b"".join(special_by_id[i].encode("utf-8") if i in special_by_id else self.vocab[i] for i in ids)
        # errors="replace": if the ids end in the middle of a character (half an emoji),
        # show the replacement mark instead of crashing.
        return data.decode("utf-8", errors="replace")

    def piece(self, token_id):
        """The text one id stands for, for printing. A half character shows as its byte values."""
        for name, i in self.special.items():
            if i == token_id:
                return name
        b = self.vocab[token_id]
        try:
            return b.decode("utf-8")
        except UnicodeDecodeError:
            return "<bytes " + " ".join(str(x) for x in b) + ">"

    # ------------------------------------------------------------------ save / load
    def save(self, path):
        """Write everything needed to rebuild this tokenizer to a JSON file."""
        data = {
            "pattern": self.pattern,
            "merges": [[a, b] for (a, b) in self.merges],   # in learned order
            "special": self.special,
        }
        with open(path, "w", encoding="utf-8") as f:
            json.dump(data, f, indent=1)

    @classmethod
    def load(cls, path):
        """Read a file written by save() and rebuild the tokenizer."""
        with open(path, encoding="utf-8") as f:
            data = json.load(f)
        tok = cls(data["pattern"])
        for step, (a, b) in enumerate(data["merges"]):
            new_id = 256 + step
            tok.merges[(a, b)] = new_id
            tok.vocab[new_id] = tok.vocab[a] + tok.vocab[b]
        tok.special = data["special"]
        return tok

22. Step 0 and the two helpers

The step-0 pattern

GPT2_SPLIT_PATTERN = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""

This is GPT-2's rule from section 6, copied from OpenAI's tiktoken. The comments above it in the file explain each alternative. r"..." is a raw string: backslashes are kept as they are, which patterns need.

count_pairs: count every neighbouring pair

def count_pairs(ids, counts, weight=1):
    """Add every neighbouring pair in the list `ids` to the Counter `counts`.

    Example: ids = [104, 101, 108, 108, 111]  ("hello")
    pairs:   (104,101) (101,108) (108,108) (108,111), each counted `weight` times.
    """
    for pair in zip(ids, ids[1:]):
        counts[pair] += weight

ids is one chunk as a list of numbers. zip(ids, ids[1:]) gives every neighbouring pair. counts is shared across all chunks, so after looping over every chunk it holds the total for each pair. weight is how many times this chunk appears in the text: if "·the" appears 211,031 times, each of its pairs is added 211,031 times in one go, instead of looking at 211,031 copies.

merge_pair: glue one pair everywhere

def merge_pair(ids, pair, new_id):
    """Return a new list where every occurrence of `pair` side by side is replaced by `new_id`.

    Example: merge_pair([104, 101, 108, 108, 111], (108, 108), 300)  ->  [104, 101, 300, 111]
    """
    out = []
    i = 0
    while i < len(ids):
        if i + 1 < len(ids) and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            out.append(new_id)   # found the pair: write the new piece, skip both
            i += 2
        else:
            out.append(ids[i])   # not the pair: copy this piece unchanged
            i += 1
    return out

Walk through the list with a position i. If the item at i and the next one are the pair, write the new id once and jump 2 ahead; otherwise copy the item and move 1. Worked example, gluing (108, 108) = "l"+"l" into 300:

23. The Tokenizer and how it trains

What a tokenizer remembers

def __init__(self, pattern=GPT2_SPLIT_PATTERN):
    self.pattern = pattern
    self.splitter = regex.compile(pattern)
    # merges: (left id, right id) -> new id. Python dicts remember insertion order,
    # so this is also the order in which the merges were learned.
    self.merges = {}
    # vocab: id -> the bytes that piece stands for. It starts with the 256 single bytes.
    self.vocab = {i: bytes([i]) for i in range(256)}
    # special tokens: name -> id, e.g. "<|endoftext|>" -> 1000. Added by hand, never learned.
    self.special = {}

Three things, matching the earlier parts: merges, the rule book in learned order (section 5's merge file); vocab, the list itself, id → bytes, starting with the 256 single bytes (section 7); special, the hand-made markers (section 12).

train: the whole of Part 2 in one function

def train(self, text, vocab_size, verbose=False):
    """Learn (vocab_size - 256) merges from `text`."""
    if vocab_size < 256:
        raise ValueError("vocab_size must be at least 256 (the single bytes)")
    if self.merges:
        raise ValueError("this tokenizer is already trained; make a new Tokenizer()")

    # Step 0: cut into chunks, and count how often each different chunk appears.
    # Most chunks repeat (" the" appears thousands of times), so we keep each different
    # chunk once together with its count. Much less work than looking at every copy.
    chunk_counts = Counter(self.splitter.findall(text))

    # Step 1: every chunk becomes its list of byte values.
    words = [[list(chunk.encode("utf-8")), count] for chunk, count in chunk_counts.items()]

    for step in range(vocab_size - 256):
        # Step 2a: count every neighbouring pair inside every chunk.
        pair_counts = Counter()
        for ids, count in words:
            count_pairs(ids, pair_counts, count)
        if not pair_counts:
            break  # every chunk is already a single piece: nothing left to merge

        # Step 2b: the most frequent pair wins. If two pairs tie, the one with the smaller
        # ids wins, so training always gives the same result for the same text.
        best = max(pair_counts, key=lambda p: (pair_counts[p], -p[0], -p[1]))
        new_id = 256 + step

        # Step 2c: glue the winner everywhere, and remember the rule.
        for word in words:
            word[0] = merge_pair(word[0], best, new_id)
        self.merges[best] = new_id
        self.vocab[new_id] = self.vocab[best[0]] + self.vocab[best[1]]

        if verbose:
            print("merge %d: %r + %r -> %r  (seen %d times)" % (
                step + 1, self.piece(best[0]), self.piece(best[1]), self.piece(new_id), pair_counts[best]))
  1. Counter(self.splitter.findall(text)): step 0, then count each different chunk. On our 22 MB of stories this turns 5,411,109 chunks into 13,119 different ones (section 6b).
  2. list(chunk.encode("utf-8")): step 1, every chunk as byte values. words is a list of [byte list, count] pairs.
  3. The for step in range(vocab_size - 256) loop runs once per merge. Asking for a list of 1,000 means 744 merges.
  4. Count all pairs with count_pairs, weighted by each chunk's count.
  5. max(..., key=lambda p: (pair_counts[p], -p[0], -p[1])) picks the most frequent pair. The key is a tuple: Python compares the count first, and only if two counts are equal does it look at the ids, so ties are always settled the same way and training is repeatable.
  6. The new piece gets the next free id, 256 + step, so ids also record the learning order.
  7. Glue the winner in every chunk with merge_pair, store the rule in merges and the new piece's bytes in vocab (the two old pieces' bytes joined).
  8. If no pairs are left (every chunk is already one piece) the loop stops early with break.

Speed: this simple version recounts every pair on every round. On a laptop it learned 8,000 merges from 22 MB in a few minutes. Real libraries (Hugging Face tokenizers, SentencePiece) only update the counts that changed, which is far faster but harder to read.

add_special_tokens

def add_special_tokens(self, names):
    """Give hand-made marker tokens the next free ids. Call this after train()."""
    for name in names:
        if name not in self.special:
            self.special[name] = len(self.vocab) + len(self.special)

Special tokens get the next free ids after the learned list. They are never produced by merging; encode looks for them by name.

24. Encoding, decoding, saving

_encode_chunk: replay the merges, earliest first

def _encode_chunk(self, chunk_bytes):
    """Turn one chunk's bytes into ids by replaying the learned merges, earliest first."""
    ids = list(chunk_bytes)
    while len(ids) >= 2:
        # Of all neighbouring pairs, find the one whose merge was learned earliest
        # (smallest new id). Pairs with no merge get "infinity", so they never win.
        pair = min(zip(ids, ids[1:]), key=lambda p: self.merges.get(p, float("inf")))
        if pair not in self.merges:
            break  # no neighbouring pair has a rule: we are done
        ids = merge_pair(ids, pair, self.merges[pair])
    return ids

Exactly section 10. Look at every neighbouring pair; among those that have a rule, take the one learned earliest (smallest new id) and glue it everywhere; repeat until no pair has a rule. self.merges.get(p, float("inf")) means "the new id of this pair's rule, or infinity if there is no rule", so pairs without a rule can never be the smallest. This is how GPT-4o turns "hello" into he, ll, hell, hello in section 10.

encode: the whole text

def encode(self, text, allow_special=True):
    """Text -> list of ids."""
    ids = []
    if allow_special and self.special:
        # Cut the text around the special tokens first, so "<|endoftext|>" becomes one id
        # instead of being spelled out as < | e n d ...
        names = sorted(self.special, key=len, reverse=True)
        parts = regex.split("(" + "|".join(regex.escape(n) for n in names) + ")", text)
    else:
        parts = [text]
    for part in parts:
        if part in self.special and allow_special:
            ids.append(self.special[part])
            continue
        for chunk in self.splitter.findall(part):
            ids.extend(self._encode_chunk(chunk.encode("utf-8")))
    return ids

First the text is cut around special tokens, so <|endoftext|> becomes its one id instead of 13 single characters. Then each normal part goes through step 0 and _encode_chunk. allow_special=False treats the markers as plain text, which matters when the text comes from users (it stops someone typing a marker that the model would trust).

decode: ids back to text

def decode(self, ids):
    """List of ids -> text. Join every piece's bytes, then read them as UTF-8."""
    special_by_id = {i: name for name, i in self.special.items()}
    data = b"".join(special_by_id[i].encode("utf-8") if i in special_by_id else self.vocab[i] for i in ids)
    # errors="replace": if the ids end in the middle of a character (half an emoji),
    # show the replacement mark instead of crashing.
    return data.decode("utf-8", errors="replace")

Join the bytes of every piece, then read them as UTF-8 (section 2b). errors="replace" handles the half-character case from section 11: if the ids stop in the middle of a character, a replacement mark is shown instead of a crash.

save and load

def save(self, path):
    """Write everything needed to rebuild this tokenizer to a JSON file."""
    data = {
        "pattern": self.pattern,
        "merges": [[a, b] for (a, b) in self.merges],   # in learned order
        "special": self.special,
    }
    with open(path, "w", encoding="utf-8") as f:
        json.dump(data, f, indent=1)

    """Read a file written by save() and rebuild the tokenizer."""
    with open(path, encoding="utf-8") as f:
        data = json.load(f)
    tok = cls(data["pattern"])

        tok.vocab[new_id] = tok.vocab[a] + tok.vocab[b]

Only the pattern, the merge list in order and the special tokens are saved; the list of pieces is rebuilt from the merges on load, exactly as during training. @classmethod means you call it on the class itself: tok = Tokenizer.load("my_tokenizer.json").

Glossary

Byte
A number from 0 to 255. Text files store characters as 1 to 4 bytes each (UTF-8).
Token
One piece of text from the tokenizer's list: a byte, part of a word, a whole word, or a special marker.
Token ID
The position number of a token in the list. This number is what the model receives.
Vocabulary
The full, fixed list of tokens (GPT-4o: 200,019 entries).
Tokenizer
The program that cuts text into tokens and turns them into IDs, and back.
Step 0 / pre-tokenization
The hand-written rule that cuts text into word-sized chunks before merging.
Merge (rule)
"Glue piece A and piece B into AB". Training produces an ordered list of these.
BPE
Byte Pair Encoding: build the list by repeatedly gluing the most frequent neighbouring pair.
Training a tokenizer
Running BPE on example text to produce the list. Counting only; no neural network.
Encoding / decoding
Text → IDs / IDs → text.
Embedding table
Inside the model: one row of learned numbers per token ID.
Special token
A hand-added marker such as <|endoftext|> that normal text cannot produce.
