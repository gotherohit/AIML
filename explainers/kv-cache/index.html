Why LLMs cache K and V, but never Q

Every price list has three prices for the same tokens. The reason is the KV cache: what keys, values and queries are, why only keys and values are worth keeping, and what that means for prompt caching, with real tests on GPT-2.

In one line: keys and values are what every past token offers the tokens after it, so they are worth keeping; a query is a question asked once, so it isn't. Caching K and V is why reading a cached prompt costs 5% of the normal price: the model isn't reading again, it is loading work already done.

Same tokens: one price 25% higher, one 95% lower. The reason is two letters, K and V, and the reason there's no Q shows how these models actually work.

One token at a time

A language model never writes a sentence. It writes one token, a small chunk of text. To pick it, it reads everything before it; then the new token joins the text and the whole thing runs again. The Transformer paper calls this auto-regressive: "consuming the previously generated symbols as additional input when generating the next".

So think about token 1,000. To write it, the model needs the 999 before it. For token 1,001 it needs the same 999 again, plus one more (Hugging Face's caching guide uses exactly this example). Almost all of that work is identical to the step before.

Attention: query, key, value

How does a token read the others? With attention, which the paper describes as "mapping a query and a set of key-value pairs to an output". An analogy helps:

  • Every token already on the page is a book in a library.
  • Its key is the label on the spine: what this token is about.
  • Its value is what's inside: the information it carries.
  • The token being processed is the reader, and it walks in with a question: its query.

The query is compared with every key: strong match, high score; weak match, low score. Then the reader takes a blend of the values, weighted by those scores. That is the whole formula:

Attention(Q, K, V) = softmax(Q·Kᵀ / √d) · V

One more rule: a token can only look backward. The paper masks the future on purpose, to "prevent positions from attending to subsequent positions". And all of this runs in every layer; GPT-2 small has 12.

The KV cache

Put the two ideas together. Generating token by token with no cache, the model recomputes the key and value of every earlier token at every step: 5 keys and values at step 5, all of those again plus one at step 6, a triangle of work that keeps growing. But the old ones come out exactly the same every time. So compute each key and value once, and keep it. That is the KV cache: each step computes 1 new key and 1 new value, appends them, and moves on.

Work per step
No cacherecompute K and V for every token so far
KV cachecompute K and V for the newest token only, read the rest from memory

I ran it on GPT-2 small on a laptop CPU: a 400-token prompt, then 200 new tokens.

RunTime
Without the cache265.39 s
With the cache13.47 s

Same output, token for token, about 20 times faster (19.7×). Another machine will give other times; the ratio is the point.

Why K and V, but never Q

Because of who uses them. A key and a value are what a token offers to everyone after it: token 3's key is read by token 4, token 5, token 500, again and again. A query is different: it is the question a token asks while it is being processed. Once that token has its answer, the question is finished. Token 500 doesn't care what token 3 asked; it only cares what token 3 has to offer.

So each step needs exactly one query, the newest token's. Hugging Face's guide says it plainly: "you only need the last token's query". You can see it in the model's attention weights on a 15-token text:

Attention shape (GPT-2)Meaning
No cache(1, 12, 15, 15)15 query rows × 15 keys, in each of 12 heads
With the cache(1, 12, 1, 15)1 query row × 15 keys

The next-token scores from the two runs differ by at most 0.00005: rounding. And inside GPT-2's cache, each layer holds exactly two things: ['keys', 'values']. Keys and values are written once and read forever; a query is asked once. Caching it would mean saving a question that's already been answered.

Why reusing them is safe

Because of the backward-only rule. A token's key and value depend only on the text before it, so adding text at the end can't change them. I tested both directions on GPT-2:

Append a sentence (14 tokens → 24) and compare every earlier key and value in all 12 layers: the largest difference was 0.00001 (1.05e-05), on values that go up to 20.6. Rounding noise.

Change one early token (token 3, " helpful" → " careful") and look at the tokens after it:

Layer01234567891011
Largest change, tokens after it00.230.390.661.401.992.341.571.141.471.341.18

The tokens before the change were untouched (0 in every layer). The tokens after it changed in 11 of 12 layers. The one that held is layer 0, whose keys and values come from each token and its position alone, before any attention has looked at other tokens. Before the change, the cache is perfect; after it, useless. That's why caching is always about a prefix.

Prompt caching: the same trick, between requests

So far the cache lives for a single reply. Prompt caching keeps it alive between requests. An agent sends the same tools and the same system prompt on every call; instead of rebuilding their keys and values each time, the provider keeps them. OpenAI's guide says it directly: "The prompt cache stores key-value (KV) tensors, not the tokens themselves." When the next request arrives and its start matches, the model picks up from saved work, which is also why the reply starts sooner: there is less to process before the first token.

The price list, explained

Cache read: 5% of the input price on Opus 5.5, Sonnet 5.5 and GPT-6.1 Sol. You're not paying the model to read again; you're paying to load work that's already done.

Cache write: 1.25× the input price on all three. The docs don't give a reason for that premium, so I won't invent one. But look at what a write has to keep. In GPT-2 small, one token goes in as one number (" helpful" is token 7613). Its keys and values across 12 layers are:

2 (K and V) × 12 layers × 12 heads × 64 numbers = 18,432 numbers
18,432 × 4 bytes (float32) = 73,728 bytes, about 74 KB, for 1 token

That's on a small, older model; hosted models don't publish their sizes, so I don't extrapolate. And the trade pays off fast:

Cached part, in units of the input priceRequest 1Request 2Total
No caching112.00
Prompt caching1.25 (write)0.05 (read)1.30

By the second request you're already ahead.

Three rules that follow from "prefix"

Rule 1: it's an exact match, from the first token. Anthropic's docs: "Cache hits require 100% identical prompt segments." On Claude the order is tools, then system, then messages. So a timestamp at the top of your system prompt quietly breaks the cache on every call (the docs' troubleshooting section names timestamps as a cause of misses).

Rule 2: it expires. Claude keeps an entry for 5 minutes, refreshed at no cost each time it's used, or 1 hour if you pay 2× on the write. OpenAI's newest models (GPT-5.6 and later) keep a prefix for at least 30 minutes after its last use.

Rule 3: there's a minimum size. 512 tokens on the newest Claude models, 1,024 on OpenAI's. Shorter than that and nothing is cached (and no error is returned).

The playbook

  1. Stable content first: tools, instructions, long documents.
  2. Changing content last: the user's question, the time, anything per request.
  3. Append, never edit the beginning of a conversation.
  4. Check the receipt. Every response reports how many tokens came from the cache: cache_read_input_tokens in Claude's usage, usage.input_tokens_details.cached_tokens on OpenAI's Responses API. If it's 0 on a repeated request, something near the top is changing.

The whole idea in one line

Three prices, two letters. Keys and values are what every past token offers the future, so they're worth keeping; a query is a question asked once. The model didn't get cheaper. It stopped redoing work it had already done.
