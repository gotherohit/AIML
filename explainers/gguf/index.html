What is inside a GGUF file, byte by byte

A local AI model is one file ending in .gguf. This is what is inside it, read byte by byte from a real 1.1 GB file, and how an engine like llama.cpp turns it into something that talks.

In one line: GGUF is not the model and not the engine. It is the container: a labelled map first, then the weights, in one file. Everything on this page was read byte by byte from a real one: qwen2.5-1.5b-instruct-q4_k_m.gguf, 1,117,320,736 bytes (1.1 GB).

Why a model needs a format at all

A model is weights: in this file, 1,777,088,000 numbers. Saved to disk, they are one long line of bytes, and bytes carry no labels. A program that opens them can't tell:

  • where one matrix ends and the next begins,
  • what shape each matrix has (1536 × 1536? 8960 × 1536?),
  • how each number is stored (32-bit float, 16-bit float, about 4 bits),
  • how many layers there are, and which piece of text each token number means.

So weights always travel with a map. In the original Qwen repository that map is spread over 7 files: model.safetensors (the weights), config.json and generation_config.json (settings), and 4 tokenizer files (tokenizer.json, tokenizer_config.json, vocab.json, merges.txt).

GGUF packs all of it into one file, in a fixed order. The specification's first sentence: "GGUF is a file format for storing models for inference with GGML and executors based on GGML", the library behind llama.cpp, the engine that runs models locally. Its stated goals include single-file deployment, mmap compatibility and "full information: all information needed to load a model is contained in the model file". Think of a shipping container with the packing list bolted to the door.

The 4 parts, in order

PartWhat it holdsIn this file
1. HeaderMagic, version, 2 counts24 bytes
2. MetadataKey and value pairs: architecture, sizes, tokenizer, chat template26 entries, about 5.9 MB (almost all of it tokenizer data)
3. Tensor index1 row per tensor: name, shape, number type, offset339 rows, 19,304 bytes
4. WeightsThe tensor data itself1,111,370,240 bytes: 99.47% of the file

Part 1: the header, byte by byte

The spec defines the header as a 4-byte magic number, a 4-byte version, and two 8-byte counts: 4 + 4 + 8 + 8 = 24 bytes. These are the first 24 bytes of the file, in hex:

47 47 55 46                  magic: the letters G G U F
03 00 00 00                  version: 3
53 01 00 00 00 00 00 00      tensor count: 339
1A 00 00 00 00 00 00 00      metadata entries: 26

Why is 47 a G? In ASCII the letter G is number 71, which is 47 in hexadecimal; U is 55 and F is 46. That's how a program knows what it's holding.

Why does 53 01 mean 339? The file is little-endian: the low byte comes first. Read it backwards, 0x0153 = 1 × 256 + 5 × 16 + 3 = 339. And 0x1A = 26. llama.cpp's own log for this file agrees: "loaded meta data with 26 key-value pairs and 339 tensors … (version GGUF V3 (latest))".

Part 2: the metadata

Keys and values, like a settings file. Some of the 26 entries in this file:

Each entry is stored as: the key text, a type code (string, 32-bit integer, array …), then the value. The very first one, general.architecture = qwen2, takes 45 bytes: an 8-byte length (20), the 20 letters of the key, a 4-byte type code (8 = string), another 8-byte length (5), and the 5 letters qwen2. Because every value is labelled, a newer file can add keys and an older program simply skips the ones it doesn't know.

Part 3: the tensor index

One row per tensor: its name, its shape, its number type, and an offset, the byte where its data starts. The first 5 rows of this file:

NameShapeTypeOffset
output.weight1536 × 151936Q6_K0
token_embd.weight1536 × 151936Q4_K191,439,360
blk.0.attn_norm.weight1536F32322,712,064
blk.0.ffn_down.weight8960 × 1536Q6_K322,718,208
blk.0.ffn_gate.weight1536 × 8960Q4_K334,007,808
Offsets count from the start of part 4, not the start of the file. Part 4 begins at byte 5,950,496 (the index ends at byte 5,950,493, then 3 bytes of padding so the data starts on a 32-byte boundary). So blk.0.attn_q.weight, 1536 × 1536, Q4_K, at offset 351,052,288, really begins at byte 5,950,496 + 351,052,288 = 357,002,784.

Part 4: the weights

Everything after the index is tensor data: 1,111,370,240 bytes, 99.47% of the file. Each tensor's bytes are laid out in its own number type, so the index is all a program needs to find and decode any of them.

How an engine reads it

  1. Read 4 bytes. If they don't say GGUF, stop: the spec calls it the "magic number to announce that this is a GGUF file".
  2. Read the metadata. It says qwen2, so the engine builds that network: 28 empty layers, waiting for weights. The file only describes the model; the engine must already know how to run a qwen2 network.
  3. Read the index. For each layer it looks up a name and gets back a shape, a type and an offset.
  4. Map the weights, don't read them. It doesn't read 1 GB up front. It memory-maps the file, and the operating system pulls in each piece when it's first used. The spec lists "mmap compatibility: models can be loaded using mmap for fast loading"; llama.cpp's log for this file shows load_mode = mmap and a "CPU_Mapped model buffer size = 1059.89 MiB", which is exactly the 1,111,370,240 bytes of tensor data.
  5. Build the tokenizer from the metadata. Now it's ready for a prompt. Given "The capital of France is", this file continued: " Paris."
"Mapped, not read in" is about loading, not zero memory. This llama.cpp build also made a 596 MiB repacked copy of some tensors for speed (CPU_REPACK), so the weights do use memory once the model runs.

Why GGUF is used

  • One file holds everything needed to load the model.
  • It loads fast, because the weights are mapped straight from disk.
  • Any precision. Every tensor names its own number type, so the same format holds 16-bit weights or squeezed 4-bit ones. The 16-bit version of this model is 3,560,416,288 bytes (3.56 GB); this Q4_K_M file is 1.12 GB.
"4-bit" is a label. This Q4_K_M file mixes 169 Q4_K tensors, 29 Q6_K and 141 F32, and llama.cpp reports it as 5.00 bits per weight (counting the weights only; counting the whole file, metadata included, gives 5.03). How those formats store a weight in 4 bits is the subject of the quantization article.

Two common claims I left out

What the letters GGUF stand for: the specification doesn't say, so I don't either. "GGUF is safe because it contains no code": it contains a chat template, and a template engine executes it, so I don't repeat that claim.

The whole idea in one line

GGUF is the container: a 24-byte header, a labelled map of settings and tensors, then the weights, in one file an engine can check, map and run.
