Quantization explained: how a 3.56 GB model fits in 1.12 GB

A model is numbers times bits. Quantization keeps every number but stores it with fewer bits. This is how it works, worked through on real weights, and what it cost when I tested 4 precisions of the same model on a 2018 laptop.

In one line: a model is numbers × bits. You can't remove numbers without changing the model, but you can store each one with fewer bits. That is quantization, and it is why a 2018 laptop with 16 GB of memory can run a real language model with no cloud and no graphics card.

A laptop from 2018

Everything on this page was measured on one ordinary machine: a Dell Inspiron 5584 with an Intel Core i7-8565U (4 cores, launched in Q3 2018) and 16 GB of memory. The model runs on the processor only, with the CPU build of llama.cpp (build b11553, 4 threads), talking to nothing but the laptop itself.

The model is Qwen2.5-1.5B-Instruct. Asked a question, its 4-bit file streamed the answer at 11.0 tokens a second (35 tokens). So how does something with 1.78 billion numbers inside run on a machine this ordinary? Two ideas: quantization, which this page is mostly about, and open weights, which is what gives you the file in the first place.

A model is a list of numbers

Take away the chat window and a model is one thing: a very long list of numbers called weights. These are the first 8 numbers of one matrix (blk.0.attn_q.weight) in the 16-bit file, read straight out of it:

0.00825  −0.00500  0.00082  0.00157  −0.00228  −0.00020  0.00482  0.00954

The whole file holds 1,777,088,000 of them. When you ask a question, your words become numbers too (for this model, "Why is the sky blue?" is the token numbers 10234, 374, 279, 12884, 6303, 30), and those are multiplied through the weights. That happens again for every token the model writes, so the whole list has to sit in memory at once. The real problem is size.

Why 1.78 billion, when the model is called "1.5B"? The model card says 1.54 billion parameters. The GGUF file stores the word table twice (once for reading text in, once for writing text out), so it contains 1.78 billion numbers. This page counts numbers in the file.

Size is numbers times bits

The size of a model is simple multiplication: how many numbers, times how much space each takes. Weights are normally stored with 16 or 32 bits each (Hugging Face's guide calls 32-bit floats "the usual"; llama.cpp describes models as usually "distributed in 16-bit format"). At 16 bits, 2 bytes each:

The count of numbers is fixed by the model. So the only thing left to shrink is the bits, and to see how, you need to know what a bit really is.

What a bit really is

A bit is a switch: on or off. One bit gives you 2 patterns, and every extra bit doubles that.

Bits124816
Patterns241625665,536

Here is the part that trips people up: 65,536 is not how big a value can get. It is how many different values you can choose from. Think of the patterns as blank labels, and you decide what they mean. Write whole numbers on 8 labels and you can store 0 to 7. Spread the same 8 labels over decimals and you can store 1.230, 1.231 … 1.237 (an illustration, not the layout of any real format).

So a decimal inside a computer is not "any number you like": it is the nearest label. Picture a ruler whose marks are the values you're allowed to store. With 65,536 marks there is almost always a mark right next to your value. With only 16 marks, your value can sit a long way from the nearest one, and it gets moved there. Storing a value as its nearest mark is called quantization.

Quantization on 8 real weights

Take the 8 weights above. They run from −0.00500 up to 0.00954. With 4 bits there are 16 labels, numbered 0 to 15; spread them evenly across that range and the gap between two labels is (0.00954 + 0.00500) ÷ 15 = 0.00097. Each weight is stored as the number of its nearest label, and turned back into a value when the model runs:

Follow the first row. 0.00825 is (0.00825 + 0.00500) ÷ 0.00097 = 13.7 gaps above the start, which rounds to label 14, so only the number 14 is stored: 4 bits. When the model runs, 14 is turned back into a value: start at −0.00500, add 14 gaps, and you get 0.00857. The model now uses 0.00857 instead of 0.00825. That small difference is the rounding error.

So where did the decimal go? It was never in the 4 bits. It comes back from 2 extra numbers, the start and the gap, which are stored once and shared by the whole group. This is the textbook formula from Hugging Face's guide, xq = round(x / S + Z): S is the gap, Z says which label stands for zero.

Why one ruler for a whole layer fails

A real layer has millions of weights, not 8. This one, blk.0.attn_q.weight, is 1536 × 1536 = 2,359,296 weights. The smallest is −2.65 and the largest 3.10, but 92.6% of them sit between −0.05 and 0.05: a few large outliers stretch the range.

Spread 16 labels across the whole range and the gap becomes (3.10 + 2.65) ÷ 15 = 0.38. Almost every weight is far smaller than that, so they all land on the same label. I tried it: all 8 weights above came back as exactly 0. Even 8 bits with one ruler for the layer (a gap of 0.0225) still turned all 8 into 0.

So real formats cut each layer into small blocks, and give every block its own start and its own gap. A block of 32 neighbouring weights spans a tiny range, so its 16 labels sit close together.

How Q4_K_M really stores weights

The popular llama.cpp format Q4_K_M is built from Q4_K, which llama.cpp's pull request 1684 describes as "4-bit quantization in super-blocks containing 8 blocks, each block having 32 weights. Scales and mins are quantized with 6 bits." Counting one block:

32 labels × 4 bits = 128 bits
+ 6-bit start (min) + 6-bit gap (scale) = 140 bits for 32 weights
140 ÷ 32 = about 4.4 bits per weight

The same page gives 4.5 once the values shared by each super-block are counted. And the "M" variant keeps some layers at 6 bits: it "uses GGML_TYPE_Q6_K for half of the attention.wv and feed_forward.w2 tensors, else GGML_TYPE_Q4_K". In my file the tensor types are 169 Q4_K, 29 Q6_K and 141 F32 (small vectors such as norms stay at full precision).

Count everything in my file and it averages 5.03 bits per number: 1,117,320,736 bytes × 8 ÷ 1,777,088,000. (llama.cpp's own load log says 5.00, because it counts only the weights, not the 5.9 MB of metadata and tokenizer at the front of the file; see the GGUF article.) That is why a "4-bit" file is not a quarter of the size: a quarter of 3.56 GB would be 0.89 GB, and the real file is 1.12 GB.

Same model, same number of weights, just fewer bits on each one. That sounds too good to be true, so I tested it.

The test: same model, 4 precisions

Qwen publishes this model officially at several precision levels, which makes a fair comparison. I downloaded 4 of them and asked each the same 70 short questions (facts and sums) on the laptop, at temperature 0, and timed 160-token answers.

FileBits per numberSizeSpeed (tokens/s, median)Score
F16 (original)16.03.56 GB4.969 / 70
Q8_08.51.89 GB6.469 / 70

Speed is the median of 5 runs per file. The laptop slows down as it heats up (the same 16-bit file gave 5.95, then 4.03, then 2.55 tokens a second in three runs back to back), so only "about 5" and "about 10" are meaningful.

Less than a third of the size, and almost nothing lost: the 16-bit and 8.5-bit files both scored 69, the 5-bit file 68. But at 3.4 bits the score fell to 42. Some of its real answers:

How much to read into this. 70 easy questions are a quick check, not a benchmark: I wrote them, and a script marks each answer by looking for the right word or number. (Every file got "How many letters are in the word banana?" wrong.) But the result matches the warning in llama.cpp's own documentation: quantization "may introduce some accuracy loss".

What you give up

1. Accuracy, and not in a smooth slope. Going from 16 to 5 bits cost 1 answer out of 70. Going to 3.4 bits cost 27. The damage arrives as a cliff, not a ramp.

2. It fails silently. I asked each file for the approximate speed of light in kilometres per second. The 16-bit file (and the 8.5-bit one) said 300,000. The 5-bit file said 300,000,000 km/s: 1,000 times too fast, and just as confident. (The real value is 299,792 km/s.) Nothing warns you which answers changed, so the only way to know is to test on your own tasks.

3. It never makes the model smarter. Quantization removes detail from numbers; it cannot add knowledge the model never had. The best a smaller file can do is match the original, and what fits on a laptop is still a small model: Mistral Large 4 has about 590 times more numbers than this one.

Not on the list: speed. The smaller file was faster on this laptop, about 10 tokens a second against 5.

Open weights: where the numbers come from

All of this depends on having the numbers in the first place. Some companies keep the weights on their own servers: you send text in, text comes back, and you never see the file. Others publish the file itself. The Open Source Initiative defines open weights as "the final weights and biases of a trained neural network".

The Qwen model here is one of them: its files are on Hugging Face under the Apache 2.0 license. Mistral said on 6 October 2026, when it launched Large 4, "We will release the weights by the end of the month."

Open weights is not open source. You get the finished numbers, but not the training data or the training code (the same OSI page makes this distinction). Still, once the file is on your disk, the model runs on your machine, offline, whenever you want.

Should you run AI on your laptop?

  • Privacy: nothing you type leaves the machine.
  • Offline: it works with no connection at all.
  • Cost: there is no price per token.
  • But: the most capable models still live in data centres.

To try it, pick a model whose Q4_K_M file is comfortably smaller than your memory; it is the format llama.cpp uses in its own example commands. Then test it on the questions you actually care about, because of point 2 above.

The whole idea in one line

A model is numbers times bits. Open weights give you the numbers. Quantization cuts the bits, from 16 down to about 5, and that's why a laptop from 2018 with no internet can run one.
