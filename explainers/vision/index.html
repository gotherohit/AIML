How LLMs see images: pixels, patches and tokens

A language model never sees pixels. It reads vectors made from small squares of the image, by an encoder trained to put pictures near the words that describe them. Here is every step, with real numbers from Qwen2.5-VL, Gemma 3 and CLIP.

STEP 0The whole answer in 4 sentences

1. An LLM doesn't really read words; it reads vectors (lists of numbers) that words are turned into.

2. So to "show" it an image, cut the image into small squares (patches) and turn each square into a vector.

3. A separate network, the vision encoder, trained on millions of images with captions, makes those vectors meaningful, and a small projector resizes them to the LLM's format.

4. Those vectors (image tokens) go into the prompt next to the word vectors, and the LLM reads them like any other token.

photo→patches→vision encoder→projector→image tokens→LLM→answer

If you remember only this, you have the core idea. Everything below is "why" and "how exactly".

STEP 1 · WHAT YOU ALREADY KNOW, LOOKED AT CAREFULLYAn LLM's real input is vectors, not IDs

You know text becomes tokens and tokens have IDs. The step people skip: the very first thing the model does with an ID is a table lookup.

  1. "Describe this photo of a cat." → tokenizer → 74785, 419, 6548, 315, 264, 8251, 13 (7 tokens; " cat" is 8,251). Real output of llama-tokenize on Qwen2.5-VL.
  2. The model has an embedding table: one row per token in the vocabulary. For Qwen2.5-VL 3B it is 151,936 rows × 2,048 numbers (in the file: token_embd.weight [2048, 151936]).
  3. ID 8,251 means only "take row 8,251". Out comes a vector of 2,048 numbers.
  4. Every layer after that works on vectors. The IDs are never seen again.
Reading the shape [2048, 151936]
GGUF (llama.cpp's format) lists a tensor's sizes innermost first: the first number is the length of one row, the last is how many rows there are. So [2048, 151936] means 151,936 rows, each 2,048 numbers long. PyTorch / Hugging Face write the same tensor the other way round: [151936, 2048]. Sanity check: the vocabulary has 151,936 tokens (the tokenizer in the same file lists exactly 151,936), and 2,048 is the model's hidden size, so the rows must be the tokens.
The key idea of the whole topic
The model doesn't need an ID. It needs a vector of the right size, in the "space" it has learned. If we can manufacture such vectors from an image, we can put them in the sequence directly, without any ID. Gemma 3's report calls these soft tokens (soft = not a discrete entry in the vocabulary).

STEP 2What a photo is to a computer

A grid of pixels; each pixel is 3 numbers (red, green, blue, 0 to 255). A real pixel from the cat's eye (at 196 × 224 size): R 34, G 79, B 105: dark blue.

A 1920 × 1080 photo = 2,073,600 pixels × 3 = 6,220,800 numbers.

Why not one token per pixel?

  • Cost. In attention, each token compares itself with every other token, so cost grows with the square of the length. 2,073,600² ≈ 4.3 trillion pairs per layer. Impossible in practice.
  • Meaning. One pixel is just a colour. "Orange" could be cat fur, a sunset, a pizza. Meaning is in groups of pixels: edges, textures, shapes.

So we want fewer, richer pieces. That's exactly what patches are.

STEP 3Patches: an image's "words"

The 2020 Google paper An Image is Worth 16x16 Words introduced the Vision Transformer (ViT). The trick is almost embarrassingly simple:

  1. Cut the image into a grid of P × P squares (P = 16 in that paper; 14 in Qwen2.5-VL and Gemma 3).
  2. Take one square: 14 × 14 pixels × 3 colours = 588 numbers. Lay them out in one row ("flatten").
  3. Multiply that row by one learned matrix → a vector of 1,280 numbers (Qwen's encoder width). This is the patch embedding. In the file: v.patch_embd.weight [14, 14, 3, 1280]: patch height, width, colours, output size.
Why is the matrix stored as [14, 14, 3, 1280]?
It is the same 588 × 1,280 matrix, just kept in the patch's shape instead of flattened. Think of it as 1,280 little filters, each one a 14 × 14 × 3 block of weights (588 numbers). Output number k of a patch = multiply the patch's 588 pixel values by filter k's 588 weights, element by element, and add them up. Do that for all 1,280 filters and you get the 1,280-number vector.

Flatten each filter and stack them side by side and you have exactly a 588 × 1,280 matrix: "flatten, then multiply by a matrix" and "slide 1,280 filters over the image, 14 pixels at a time" are the same arithmetic. Code implements it as a convolution with kernel 14 and stride 14 because that does it for every patch at once, and stores the weights in that 4-D shape (again innermost first: 14 wide, 14 high, 3 colours, 1,280 filters).
The maths, on a toy image you can check by hand

Nothing is ever multiplied "in 4-D". Two separate things happen: cutting (just rearranging numbers, no maths) and then one ordinary 2-D matrix multiplication.

Compare with text: a word → a row of the embedding table. A patch → its pixels × a matrix. Both end as a vector. That is why the paper says an image is "worth 16 × 16 words".

STEP 4Position: where was this patch?

You know this from text: attention itself has no notion of order, so LLMs add position information (today usually RoPE). Same problem here, but in 2D: shuffle the patches and the bare transformer sees the same set.

  • Original ViT: add a learned position vector to each patch (one per grid slot). You can see it in Gemma's encoder file: v.position_embd.weight with 4,096 slots = 64 × 64 patches.
  • Qwen2.5-VL: 2D RoPE: the rotation encodes the row and the column, so the model knows "above" and "left of".

STEP 5The vision encoder: a transformer whose tokens are patches

Good news: you already understand it. It's the same machine as an LLM (layers of attention + MLP), with two differences: the tokens are patch vectors, and it doesn't predict a next token; it just outputs one improved vector per patch.

Why it's needed. After step 3, a patch vector only describes its own 14 × 14 square ("dark blue, a curved edge"). Attention lets every patch look at others and mix in what it finds. After many layers, the vector for that patch carries context: it's part of an eye, of a cat, looking at the camera. (That phrase is a description for understanding; nobody can read such a label out of the numbers.)

In llama.cpp that separate file is the mmproj GGUF ("multimodal projector"). It contains the encoder and the projector, despite the name.

STEP 6CLIP: who taught the encoder what a cat is?

Nobody labels millions of patches by hand. The most influential answer is CLIP (OpenAI, 2021). Take this one slowly; it's the heart of the story.

  1. Data: 400 million images with the text found next to them on the internet (captions, alt text).
  2. Two encoders: an image encoder (image → vector) and a text encoder (caption → vector), both producing vectors of the same size.
  3. The game: take a batch of N pairs. Compute the similarity of every image with every caption: an N × N table. The N matching pairs are on the diagonal. Training pushes diagonal scores up and all the others down.

That's what makes the image vectors meaningful in a "language-like" way, which is exactly what an LLM later needs.

Why are the numbers so small?
Cosine similarity goes from −1 to 1, and CLIP's matching pairs typically sit around 0.3. Only the ranking matters. Before turning scores into probabilities, CLIP multiplies them by a learned scale (100 in this model), so 0.294 vs 0.246 becomes a big gap: cat 98.9%, tiger 0.8%, dog 0.1%, rabbit 0.1%, car 0.02%. That's zero-shot classification: it was never trained on this 5-way choice.

SigLIP (Google, 2023) changes only the scoring: each cell of the table is its own yes/no question (sigmoid), instead of a softmax across the whole row. Same idea, cheaper to scale. Gemma 3 uses a 400M SigLIP encoder. Qwen2.5-VL trained its own encoder from scratch; one of its stages was CLIP-style training.

STEP 7The projector: the adapter between two networks

The encoder speaks "1,280 numbers per patch"; Qwen's LLM expects 2,048, and even matching sizes wouldn't mean matching meanings: number #7 in one space has nothing to do with number #7 in the other. So a small network sits between them, like a plug adapter.

  • LLaVA (2023): a single matrix. H = W · Z: Z = encoder output, W = learned matrix, H = vectors the size of word vectors. First trained with encoder and LLM frozen, on 595,000 image-caption pairs; the paper calls this "training a compatible visual tokenizer for the frozen LLM".
  • LLaVA-1.5: a 2-layer MLP instead of one matrix. Still the common design.
  • Qwen2.5-VL (the "2 × 2 merge", explained in the box below): first glue each 2 × 2 block of neighbouring patch vectors together (4 × 1,280 = 5,120 numbers), then a 2-layer MLP to 2,048. File tensors: mm.0 [5120 → 5120], mm.2 [5120 → 2048]. Effect: 4× fewer tokens. Our cat: 4,060 patches → 1,015 image tokens, each covering 28 × 28 pixels.
  • Gemma 3: 896 × 896 image → 64 × 64 = 4,096 patches → average each 4 × 4 block → 16 × 16 = 256 tokens, always → one matrix from 1,152 (SigLIP width) to 2,560 (Gemma 3 4B's width).
The 2 × 2 merge, step by step
  1. After the encoder, every 14 × 14 patch has its own vector of 1,280 numbers. The cat has a grid of 58 × 70 = 4,060 of them.
  2. Group the grid into squares of 2 × 2 neighbouring patches (top-left, top-right, bottom-left, bottom-right). Together they cover 28 × 28 pixels. 58 × 70 patches → 29 × 35 = 1,015 groups.
  3. In each group, lay the 4 vectors end to end: 4 × 1,280 = 5,120 numbers. Nothing is averaged or thrown away yet.
  4. Pass those 5,120 numbers through the small 2-layer network (mm.0: 5,120 → 5,120, then mm.2: 5,120 → 2,048). Out comes one vector of 2,048: one image token.
Why: the LLM is the expensive part, and every token costs it compute and context. Merging gives it 4× fewer tokens (1,015 instead of 4,060), while the network still sees all 4 patches' details and can learn what to keep. Gemma's 4 × 4 average pooling is a cruder version of the same idea: it simply averages 16 patch vectors into one.
Patch vs token, don't mix them up
Patch = what the encoder works on (14 × 14 px). Image token = what the LLM receives after the projector (Qwen: 2 × 2 patches = 28 × 28 px; Gemma: 4 × 4 patches pooled). In this article, "tokens" always means the LLM side.

DEEP DIVE · THE ACTUAL ARITHMETICFrom pixels to image tokens, with only 2-D matrix multiplication

The natural follow-up questions: what the higher-dimensional shapes mean, what a convolution is, who does the reshaping, how the feed-forward layer treats tokens, and where batches fit. Every result here was checked by running it in PyTorch or NumPy.

A. Higher-dimensional shapes are bookkeeping

The one rule
A reshape never changes a number. It copies the same values into a table with different rows and columns. Every 3-D, 4-D or 5-D shape in a model is the same numbers regrouped so that the next step can be an ordinary 2-D multiplication: (m × n) · (n × k) = m × k, where the shared n disappears.

You can't multiply the image and the weights directly. In NumPy, img @ W with the image as 980 × 812 × 3 and the weights as 14 × 14 × 3 × 1280 fails with ValueError: operands could not be broadcast together. On arrays with more than 2 dimensions, @ multiplies only the last two dimensions of each (a batched multiply, see G), and these don't line up. The image has to be cut into patch rows first.

B. The toy patch multiplication

See the box in step 3: a 4 × 4 grey image is cut into four 2 × 2 patches, which become a 4 × 4 matrix X (one row per patch). Two filters are flattened into columns, giving W (4 × 2). X · W gives 14, 22, 46, 54 for "brightness" and −2 everywhere for "left minus right". In NumPy, the cutting step for the real cat looks like this:

X = img.reshape(70, 14, 58, 14, 3)   # split height into 70×14, width into 58×14
       .transpose(0, 2, 1, 3, 4)     # bring the "which patch" axes to the front
       .reshape(4060, 588)           # one row per patch: 14×14×3 = 588 numbers
out = X @ W.reshape(588, 1280)       # (4060 × 588) · (588 × 1280) = 4060 × 1280

Checked: one patch's sum computed manually matches its row in out.

C. What a convolution is (and what "2D" and "3D" mean)

A convolution is a small block of weights (a filter, or kernel) that slides over the data. At each position it multiplies the numbers under it by its weights and adds everything up into one output number. The stride is how far it jumps between positions.

The "D" counts sliding directions, not channels
Colour channels are never slid over: a filter always covers all 3 colours at once and sums over them.

D. Qwen2.5-VL, step by step, for our cat

Read from the Hugging Face transformers source (image_processing_qwen2_vl.py, modeling_qwen2_5_vl.py) and the vision file used in the demo.

  1. Input. 2,306 × 1,920 × 3 numbers (height × width × colour).
  2. Resize (image processor) to fit the token budget, both sides a multiple of 28 (patch 14 × merge 2): 980 × 812 × 3.
  3. Normalise each value: (v / 255 − mean) / std per colour, using CLIP's values (red: mean 0.481, std 0.269). Same shape.
  4. Two frames. Qwen's unit spans 2 video frames, so a photo is copied: 2 × 980 × 812 × 3.
  5. Cut and write rows (image processor, no maths). 70 × 58 = 4,060 patches; each holds 3 colours × 2 frames × 14 × 14 = 1,176 numbers, copied into one row in a fixed order. The patches are ordered so that each 2 × 2 group of neighbours is 4 consecutive rows. → X: 4,060 × 1,176.
  6. Patch embedding (first layer of the encoder). 1,280 filters of 1,176 weights, stored as (1280, 3, 2, 14, 14); flattened, they form W: 1,176 × 1,280. Y = X · W → 4,060 × 1,280. In code this is nn.Conv3d with kernel = stride = (2, 14, 14), the same arithmetic. llama.cpp uses two 2-D kernels (v.patch_embd.weight and .weight.1, one per frame) and adds them. For a still image both frames are identical, so "588 numbers in, 1,280 out" is accurate.
  7. Position. No numbers added; each patch keeps its (row, column), and 2D RoPE uses it inside every attention layer.
  8. 32 layers, each 4,060 × 1,280 in and out. Inside: Q = Y·Wq, K = Y·Wk, V = Y·Wv (each W 1,280 × 1,280); scores Q·Kᵀ (4,060 × 4,060 in layers 7, 15, 23, 31; 64 × 64 per 8 × 8 window in the other 28); softmax; scores · V; feed-forward 1,280 → 3,420 → 1,280; normalisations and adding back the input.
  9. Merge + projector (PatchMerger): RMSNorm → glue 4 consecutive rows, view(-1, 5120): 1,015 × 5,120 → · (5,120 × 5,120) → GELU → · (5,120 × 2,048) → 1,015 × 2,048.
  10. Into the LLM. These 1,015 rows overwrite the 1,015 <|image_pad|> rows of the prompt's embeddings.

E. Who does the reshaping: a library, or people by hand?

  • The library can do it all in one call. F.conv3d(video, w, stride=(2, 14, 14)) with video (1, 3, 2, 980, 812) and w (1280, 3, 2, 14, 14) returns (1, 1280, 1, 70, 58): 1,280 numbers for each of the 70 × 58 patches. Checked: identical to the manual "reshape to 4,060 × 1,176, then multiply". For 2-D there are nn.Conv2d and F.unfold (which just cuts out the patches). Plain NumPy has no such function; you write the reshape yourself.
  • Qwen's code is half and half. Its image processor does the resize, 2-frame copy, cutting and flattening by hand (reshape/permute lines written by the Qwen team). That lets images of different sizes be packed into one list (see G), puts 2 × 2 neighbours in consecutive rows for the merge, and records the grid size for positions and windows. The model then uses the library's nn.Conv3d on each patch-sized block.
  • Everything else uses library building blocks: nn.Linear (a 2-D multiply plus a bias), softmax, normalisation. The model's authors write the reshapes between them, like view(-1, 5120).

F. The feed-forward layer: one network, each token on its own

There is one feed-forward network (one set of weights). All tokens go through it together as one matrix multiply, but each token is processed independently.

input X (5 × 2)X · W1 (5 × 3)· W2 → (5 × 2)
token 11 01 0 12 1
token 20 10 1 11 2
token 31 11 1 23 3
token 42 02 0 24 2
token 50 20 2 22 4

W1 = [[1 0 1], [0 1 1]], ReLU between (no negatives here), W2 = [[1 0], [0 1], [1 1]].

Output row 3 depends only on input row 3: push token 3 through alone and you get [3 3] again. So "5 copies in parallel" is right if the copies share identical weights, and "one after another" gives the same numbers, just slower. The library does one multiply, e.g. (4,060 × 1,280) · (1,280 × 3,420) in Qwen's encoder. Qwen's version adds a gate matrix, still row by row. The original Transformer paper calls this layer position-wise.

The split of work in a layer
Attention: tokens exchange information (the only place they interact). Feed-forward: each token processes what it now holds, alone, with the same weights as every other token.

G. Batches: many prompts or images at once

A batch adds one dimension: (B prompts, T tokens, d numbers), e.g. (2, 5, 2).

  • Feed-forward ignores the batch: reshape (2, 5, 2) → (10, 2), multiply, reshape back. To this layer, 2 prompts of 5 tokens look like 10 tokens.
  • Attention keeps prompts separate: a token may only look at its own prompt, so you get 2 separate 5 × 5 score tables, not one 10 × 10. Q (2, 5, d) · Kᵀ (2, d, 5) = (2, 5, 5). This batched matrix multiply is what @ does on 3-D arrays: the last two dimensions are multiplied, once per entry of the first.
  • Different lengths: either pad short prompts with dummy tokens plus a mask (their scores set to −∞ before softmax, so weight 0), or pack everything into one long list and record the boundaries.
  • Qwen's vision encoder packs. Two images of 4,060 and 1,200 patches become one list of 5,260 rows plus boundaries, cu_seqlens, so attention never mixes patches from different images. The window layers do the same per 8 × 8 window with cu_window_seqlens. (Both are in Qwen's attention code.)
  • The demo here used a batch of 1. Servers batch many users' prompts; the maths per token is the same.

STEP 8Inside the LLM: the image becomes part of the prompt

Qwen's chat format around the image (real special-token IDs from the model):

<|vision_start|> (151652) · <|image_pad|> × 1,015 · <|vision_end|> (151653) · "Describe this image in 2 sentences."

  1. The prompt is tokenized with one <|image_pad|> placeholder per image token.
  2. After the embedding lookup, before layer 1, each placeholder's vector is replaced by one image vector from the projector.
  3. From then on it's a normal forward pass. When the model writes "blue", attention lets that position look back at all 1,015 image positions, exactly like looking back at earlier words.

Positions: Qwen's MRoPE gives each image token (row, column); text tokens get a plain counter. That's how "eyes above nose" survives into the LLM.

Read, not write: image vectors are not rows of the vocabulary table; the output layer can only choose among the 151,936 vocabulary entries. So this design can read images but not produce them.

Cost on a laptop CPU: encoding the cat into 1,015 tokens took 54.6 s on CPU, before the first word of the answer.

STEP 9Training in stages: why freeze things?

You glue together two networks that were trained separately. If you trained everything at once from the start, the random new projector would send garbage into the LLM and could damage what it already knows. So: first train the glue, then loosen the rest.

STEP 10Resolution is a budget (real experiments)

More pixels → more patches → more tokens → more compute and context. So systems cap it and shrink the image first. Whatever is too small after shrinking is gone before the model sees anything.

Lesson: a big obvious feature (eye colour) survives a tiny budget; fine detail (small letters) needs many tokens. The eye chart uses random letters so the model can't guess words from context. Google saw the same in Gemma 3's report: document-reading score 31.9 → 45.4 → 59.8 as encoder resolution goes 256 → 448 → 896.

Tiling is the workaround: cut a big image into several full-resolution crops (Gemma's Pan & Scan; InternVL's 1 to 40 tiles of 448 × 448 plus a small thumbnail of the whole). More detail, more tokens.

STEP 11What an image costs in an API

Anthropic's docs: "Claude views images in patches instead of pixels. Each patch is a 28×28-pixel block of the image, referred to as a visual token." Tokens = ⌈w/28⌉ × ⌈h/28⌉, with caps (Claude 4.7 and later: 2,576 px long edge, 4,784 tokens; other models: 1,568 px, 1,568 tokens). OpenAI's docs describe 32 × 32 px patches for some models, with a 2,500-patch budget at high detail on several.

STEP 13Why it still fails

  • Small text: shrunk below a patch → becomes texture. (Eye chart.)
  • Counting: true 4 / 9 / 17 / 38 → Qwen 4, 10, 15, 30; Gemma 5, 8, 21, 47. 1 right of 8, worse as counts grow. There's no counting step; the number is predicted like any token. Anthropic's docs say counts are approximate with many small objects.
  • Exact positions: approximate (Anthropic's docs say to verify coordinates).

These are small 3B/4B models in 4-bit on a CPU; bigger models do better. The mechanism, and the reason for these failure types, is the same.

STEP 14Common confusions to avoid

"The LLM looks at the image."No: it receives vectors made from a shrunk copy. The encoder did the "looking"; the LLM reads the result.
"CLIP is the model that answers."No. CLIP is a training method (and a model) that produces an image encoder whose outputs line up with text. The answering is done by the LLM.
"Image tokens are words from the vocabulary."No: they are vectors that match no vocabulary row (except in designs like Chameleon, which add image codes to the vocabulary).
"Patches and image tokens are the same thing."In Qwen, 4 patches become 1 token; in Gemma, 4,096 patches become 256 tokens. In the original ViT, yes, 1 patch = 1 token.
"The projector is big."No, it's tiny next to the encoder and LLM (Qwen's is about 37M of the 669M in the vision file). Its job is translation, not understanding.
"More resolution is always better."Better detail, but more tokens: slower, pricier, and uses context. That's the trade-off the budget chapter shows.

STEP 15Check yourself

1. Why can image vectors be inserted into a text model at all?Because after the embedding lookup an LLM only works with vectors; any vector of the right size, in the space it understands, can occupy a position.
2. How many numbers in one Qwen patch, and what comes out?14 × 14 × 3 = 588 in; a 1,280-number vector out (via v.patch_embd).
3. Why do patches need positions?Attention treats input as a set; without positions a shuffled image is identical to the original.
4. In CLIP training, what's pulled together and what's pushed apart?Each image with its own caption is pulled together; with every other caption in the batch it's pushed apart.
5. What does the projector do in Qwen, and why the 2 × 2 merge?Joins 4 neighbouring patch vectors (5,120 numbers) and maps them to 2,048 for the LLM; cuts the token count by 4.
6. Our cat: patches and tokens?812 × 980 → 58 × 70 = 4,060 patches → 1,015 image tokens.
7. Why did 56 tokens answer "blue" but fail the eye chart?Eye colour is a big feature that survives shrinking; small letters fall below one patch and disappear.
8. How does Claude count image tokens?⌈w/28⌉ × ⌈h/28⌉ after resizing within its cap; 1000×1000 → 1,296.
9. Why can't this design draw images?Its output layer only picks from the text vocabulary; image vectors aren't in it.
10. One-line summary?An LLM never sees pixels; it reads vectors made from patches, trained to sit near the right words.
11. Why can't you just do img @ W with the 4-D weights?The shapes don't line up for a 2-D multiply. First cut the image into a 4,060 × 588 (or 1,176) table of patch rows; then it's (4,060 × 588) · (588 × 1,280).
12. What does the "3D" in Conv3d count, and where do the colours go?The directions the filter slides: time, height, width. Colours are always fully inside the filter and summed over.
13. Do 5 tokens go through the feed-forward layer one by one or together?Together as one 5-row matrix multiply with one shared set of weights, but each row is computed independently: tokens only interact in attention.
14. How does a batch of prompts fit in?Feed-forward treats all tokens of all prompts as rows. Attention keeps a separate score table per prompt (batched multiply), using padding + mask or packing with boundaries (Qwen's vision encoder packs, with cu_seqlens).

ViTVision Transformer: a transformer whose tokens are patches

CLIP / SigLIPtraining an image encoder and text encoder so matching image-caption pairs get close vectors
Zero-shotdoing a task it wasn't trained for, e.g. picking the closest of 5 captions
Projector / connectorsmall network mapping encoder vectors into the LLM's embedding size
