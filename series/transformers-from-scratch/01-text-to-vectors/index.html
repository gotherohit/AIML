CoreA model can only do arithmetic

Inside, a language model is a long chain of arithmetic, mostly multiplications and additions. It cannot read letters. So step one is always the same: turn the text into numbers.

That happens in two moves, and this episode is about both:

  1. Text → token IDs. Split the text into pieces and give each piece its number from a fixed list.
  2. Token IDs → vectors. Swap each ID for a long list of numbers that the model can actually compute with.

CoreStep 1: text becomes token IDs

GPT-2's tokenizer has a list of 50,257 pieces. Each piece has a number, its token ID. Our sentence becomes 4 pieces:

The464·cat3,797·sat3,332·on319

The dot · is a space. Most words carry the space in front of them, so " cat" (with the space) is one piece. Capitals and spaces make different pieces:

catID 9,246
·catID 3,797
·CatID 5,181
·catsID 11,875
CatID 21,979

How that list of pieces is built (BPE) is the whole subject of the tokenizer article and video, so here we just use it.

Now the model has [[464, 3797, 3332, 319]]: one sentence of 4 whole numbers. Its shape is [1, 4]: B = 1 sentence (the batch size) and T = 4 tokens. GPT-2's code always works on a batch of sentences, [B, T], and a single sentence is just a batch of 1. We will track the shape of the data at every step of the series.

Why [1, 4], and not [4] or [4, 1]?

Same 4 numbers, three different shapes:

[4]a plain list, one dimension: [464, 3797, 3332, 319]
[4, 1]a table of 4 rows × 1 column: [[464], [3797], [3332], [319]]
[1, 4]a table of 1 row × 4 columns: [[464, 3797, 3332, 319]]

We use [1, 4], exactly what GPT-2's code uses: tok("The cat sat on", return_tensors="pt").input_ids has shape [1, 4]. The shape matters for the next step, because the lookup keeps the IDs' shape and adds 768 on the end: [1, 4] gives [1, 4, 768]. Dropping the batch dimension, [4] would give [4, 768]: the same numbers, but the code always keeps B, so we do too. [4, 1] would give [4, 1, 768], which is wrong: it reads as 4 sentences of 1 token each.

CoreWhat goes into the tokenizer, and what comes out

In: plain text, a string of characters. For one prompt, that's just "The cat sat on". For training, it's a huge pile of documents, each one a single string, however long (the next section shows what that means for lines and books). GPT-2 was trained on WebText: the text of web pages linked from Reddit posts with at least 3 karma (net upvotes), which the paper describes as "slightly over 8 million documents for a total of 40 GB of text" (with Wikipedia pages removed).

Out: for each text, a list of token IDs. Different texts give lists of different lengths:

“The cat sat on”[464, 3797, 3332, 319]4 IDs
“My dog”[3666, 3290]2 IDs
“Once upon a time”[7454, 2402, 257, 640]4 IDs

That detail matters for batches: the tokenizer hands back a ragged list (rows of different lengths), not a neat table. Turning it into a table with a fixed shape is a separate step, the "Make the ID table" box in the diagram, and it happens in different places:

  • Decoding (padding): the tokenizer library does it, but only when asked. With Hugging Face, tok(texts, padding=True, return_tensors="pt") returns the padded [B, T] table and the attention mask. GPT-2's tokenizer has no pad token, so on its own it refuses ("Asking to pad but the tokenizer does not have a padding token"); you first set tok.pad_token = tok.eos_token.
  • Pretraining (packing): not the tokenizer. Separate data-preparation code joins the tokenized documents into one long stream and cuts rows from it.

Both are covered in the batch sections below.

The shapes, start to finish
n texts (strings) → tokenizer → n lists of IDs, each its own length (here 4, 2, 4)
• decoding, padded: [n, T], T = the longest prompt (here [3, 4])
• pretraining, packed: [B, T], T chosen by you, B = total tokens ÷ T, usually not n (our 3 documents make 23 tokens: T = 6 gives [3, 6], T = 4 gives [5, 4])

The tokenizer itself is not part of the network's learned numbers. It's a fixed list of pieces plus a list of merge rules (in the Hugging Face copy of GPT-2, the files vocab.json and merges.txt; OpenAI's release calls them encoder.json and vocab.bpe), built once before training and never changed by it. How it splits text into pieces is the whole subject of the tokenizer article; this series starts from its output.

CoreOne document in, one list out (lines are just characters)

“Do we give it a book, paragraphs and paragraphs, or 100 numbered lines? And if it's one long document, does it still give a ragged list?”

The tokenizer doesn't know about lines, paragraphs or pages. Its input is one string: one long run of characters, of any length. A line break is not a structure, it's just one more character (\n), and it gets a token like any other.

Here is a small document with 3 lines and a blank line, written as one Python string, 61 characters:

doc = "The cat sat on the mat.\nIt was warm.\n\nLater, the dog came in."

The real GPT-2 tokenizer gives back one flat list of 21 IDs. The ↵ \n tiles are the line breaks (ID 198); the blank line is just a second line break in a row:

The464·cat3,797·sat3,332·on319·the262·mat2,603.13↵ \n198It1,026·was373·warm5,814.13↵ \n198↵ \n198Later18,602,11·the262·dog3,290·came1,625·in287.13

No "line 1, line 2", no rows: one string in, one list out. tok.decode(ids) gives back exactly the same string, line breaks included, so nothing about the layout is lost; it's all in the IDs.

A long document is still one list. The same paragraph repeated 1,000 times is 63,000 characters and comes back as one list of 22,999 IDs. A whole book is one string too, and one list of (for a novel) well over 100,000 IDs. The tokenizer doesn't care that GPT-2 can only read 1,024 tokens at once; Hugging Face only prints a warning ("Token indices sequence length is longer than the specified maximum sequence length for this model (22999 > 1024)"). Cutting the list down to size is a later step (packing, below).

So where does the ragged list come from?

From giving the tokenizer several strings at once (a Python list of strings). Each string gets its own list, and they have different lengths. So "n texts" means n separate strings: n prompts, or n documents. Three documents, the first being the one above:

document 0“The cat sat on the mat.↵It was war…”21 IDs
document 1“Paris is the capital of France.”7 IDs
document 2“Hello!”2 IDs

A ragged list is a list of lists: [[464, 3797, 3332, …], […], […]], lengths 21, 7, 2. One document on its own is just one list (a "ragged list" of 1).

What if you cut the document into lines yourself?

You could pass the lines as separate strings (doc.splitlines()), and you would get a ragged list, one per line:

“The cat sat on the mat.”[464, 3797, 3332, 319, 262, 2603, 13]7 IDs
“It was warm.”[1026, 373, 5814, 13]4 IDs
“”[]0 IDs
“Later, the dog came in.”[18602, 11, 262, 3290, 1625, 287, 13]7 IDs

But splitlines() throws the line breaks away, so the model would never see them. Joined back, that's 18 IDs instead of 21, and decoding gives "The cat sat on the mat.It was warm.Later, the dog came in.": the layout is gone. (Keeping the breaks, with splitlines(keepends=True), gives the same 21 IDs here, so it would just be extra work.) That's why datasets keep each document as one string, line breaks and all.

Who decides what one "document" is?

The dataset does. In WebText, one document is the text of one web page. OpenAI collected 45 million links from Reddit, pulled the text out of each page's HTML with two text extractors (Dragnet and Newspaper), then removed duplicates and cleaned it: "slightly over 8 million documents for a total of 40 GB of text". So it's about 8 million documents (45 million is the number of links), and each one is a single string, often many paragraphs long. GPT-2 itself never sees "documents" or "lines", only token IDs.

What pretraining does with all those lists

The ragged list barely lives: the data-preparation code tokenizes each document, puts the end-of-text token (ID 50256) after it, and joins everything into one giant list. This is nanoGPT's real code for OpenWebText (an open re-creation of WebText: 8,013,769 documents). It's plain Python using tiktoken, OpenAI's fast tokenizer library, which gives the same GPT-2 IDs:

def process(example):                       # one document = one string, example['text']
    ids = enc.encode_ordinary(example['text'])  # one string -> one list of IDs
    ids.append(enc.eot_token)                   # 50256 marks where the document ends
    ...
arr_batch = np.concatenate(batch['ids'])    # all the lists, end to end, into one array

The result, train.bin, is one flat array of about 9 billion IDs (nanoGPT's comment: 9,035,582,198). The only trace of where one document ended is the end-of-text token. Then, at every training step, get_batch picks B random starting points in that array and copies T = 1,024 IDs from each, which gives the [B, T] table. Our 3 documents become one stream of 21, 7, 2 + 3 end-of-text tokens = 33 IDs.

One document vs many
one string (any length, line breaks and all) → tokenizer → one flat list [N]
n strings → tokenizer → n lists of different lengths (ragged)
• pretraining: every list + end-of-text, joined into one stream → cut into [B, T]
• decoding: pad the n lists to the longest → [n, T]
“And how does the output mean anything?”

On its own it doesn't. An ID is only a row number in the vocabulary: 3797 is " cat" because that's where " cat" sits in the list, not because the number says anything about cats. The tokenizer's job is just to turn text into IDs and back (decode) without losing anything. Meaning starts in the next step: each ID picks a row of 768 numbers from the token table, and those numbers were learned in training. The layers after that (Episodes 2-4) turn them into a prediction.

CoreWhy an ID alone is useless

An ID is just a name tag. " cat" is 3,797; " dog" is 3,290. Nothing about those two numbers says the words are similar, and ID 3,798 is not "a bit more cat". Doing arithmetic on name tags would be meaningless.

What the model needs instead is, for every token, a list of numbers where similar words get similar lists. A list of numbers like that is called a vector, and how many numbers it has is its dimension. In GPT-2 small every token becomes a vector of 768 numbers.

You can think of the 768 numbers as 768 "dials". No single dial has a name like "is an animal"; the meaning is spread across all of them. But together they place the word somewhere in a 768-dimensional space, and words used in similar ways end up close to each other.

CoreStep 2: the embedding table

GPT-2 stores one vector for every token in one big table, the token embedding table (in the code it's called wte):

  • 50,257 rows, one per token ID
  • 768 columns, one per dial

Its shape is [50257, 768]. That's 38,597,376 numbers, 31.0% of the whole model, about 154 MB at 4 bytes each.

Turning an ID into a vector is just: go to that row and copy it. ID 3,797 → row 3,797. Here are the first 4 of the 768 numbers in each of our rows:

row 464 (The)[ -0.0686, -0.0203, +0.0645, -0.0621, … ]
row 3,797 (·cat)[ +0.0100, +0.0366, +0.1640, -0.2185, … ]
row 3,332 (·sat)[ +0.0207, -0.1156, +0.0208, -0.2426, … ]
row 319 (·on)[ -0.0496, +0.0518, +0.0353, +0.0501, … ]

Stack the 4 rows and you get one sentence of 4 rows and 768 columns: shape [1, 4, 768]. One row per token, in sentence order.

[1, 4] IDs  →  look up rows in [50257, 768]  →  [1, 4, 768]

CoreMatrix multiplication, from zero

Every later episode is built mostly around one operation: matrix multiplication. Here it is on tiny tables, so the rule is clear before we meet it at full size.

A matrix is a table of numbers. Its shape is [rows, columns]. To multiply A by B:

  1. Take a row of A and a column of B. They must be the same length.
  2. Multiply them pair by pair and add it all up. That one number is called a dot product.
  3. Do this for every row of A with every column of B. Row i, column j of the answer = row i of A · column j of B.

Go deeperThe lookup is secretly a multiplication

Copying a row looks different from multiplying, but it's the same thing. Write each ID as a one-hot row: 50,257 zeros with a single 1 in the ID's position. For a vocabulary of 8 and ID 3:

00010000

Multiply that row by the table. Every row of the table gets multiplied by 0 except one, which gets multiplied by 1. So the answer is exactly that row.

one-hot [1, 4, 50257] × table [50257, 768] = [1, 4, 768]

The 1 in front (the batch of one sentence) just comes along; how multiplication works with 3 dimensions is shown further down.

The shape rule works: 50,257 matches 50,257 and disappears. Real code doesn't do this, because multiplying by 50,257 zeros is a waste. It just copies rows (OpenAI's GPT-2 code uses tf.gather, which means "pick these rows"). Thinking of it as a multiplication still pays off: in Episode 4 GPT-2 multiplies by this same table again, at the very end, to score every word (OpenAI's code: tf.matmul(h_flat, wte, transpose_b=True)).

You'll check this yourself in the notebook: both ways give identical numbers.

Nobody wrote these 38.6 million numbers. Before training they are random. Training (Episodes 5 to 8) nudges them a tiny bit at a time, over and over, so that the model predicts next words better. Words used in similar places get nudged in similar ways, and their rows drift together.

CoreThe missing piece: word order

Look at what we have so far. The row for " cat" is the same whether " cat" is the first word or the hundredth. So if we shuffled our 4 pieces into [319, 3332, 3797, 464], we'd get exactly the same 4 rows, just in a different order. (Typing "on sat cat The" isn't quite the same test: "on" without a space and " The" with one are different pieces, as we saw above.)

That matters because the next step, attention (Episode 2), compares rows with each other, and the comparison itself doesn't look at where a row sits. Without help, word order would be almost invisible (there's one subtle leak, see the Deeper box "Do models even need position rows?" below).

GPT-2's fix is simple: a second table, the position table (wpe), with one row per position:

  • 1,024 rows: position 0, 1, 2, … 1,023
  • 768 columns, the same width as the token rows

Shape [1024, 768], 786,432 numbers. This table is also why GPT-2 can read at most 1,024 tokens at once: there is no row for position 1,024.

row 0 (position 0)[ -0.0188, -0.1974, +0.0040, +0.0113, … ]
row 1 (position 1)[ +0.0240, -0.0538, -0.0949, -0.0129, … ]
row 2 (position 2)[ +0.0042, -0.0848, +0.0545, -0.0047, … ]
row 3 (position 3)[ -0.0003, -0.0738, +0.1055, +0.0007, … ]

Like the token table, these rows are learned during training. The original Transformer paper used fixed sine and cosine waves instead, and said learned positions gave "nearly identical results". GPT-1 and GPT-2 chose learned ones.

CoreMany texts at once: the batch

Models almost never run one text at a time. Training feeds hundreds of rows per step, and running many prompts together is far faster than one by one. Putting several rows of tokens into one table is called a batch. Nothing new in the shape: the batch dimension we've carried since Step 1 just gets bigger than 1.

one text: IDs [1, T] → vectors [1, T, 768] (B = 1)
a batch: IDs [B, T] → vectors [B, T, 768]

B is how many rows (the batch size) and T is how many positions each row has. A row can be one prompt, or, in training, a slice of text. A [B, T, 768] block is just B sheets of [T, 768], one per row, stacked one behind the other.

The embedding step doesn't change at all. Every ID in the [B, T] table still looks up its own row, and every position still gets its position row. As in Step 3, the position rows [T, 768] are the same for every row of the batch (position 2 is position 2 in every row), so one copy is added to all B sheets: that's broadcasting, and now you can see it with 3 rows.

token rows [B, T, 768] + position rows [T, 768] (copied to every text) = [B, T, 768]
“Wait: [B, T] and [50257, 768] don't fit the multiplication rule?”

Right, and they don't need to, because this step is a lookup, not a multiplication. A token ID is a row number (an address), not an amount. 3797 × the table would mean nothing; "go to row 3797 and copy it" is what happens.

The lookup rule: the result's shape is the shape of the IDs, plus the shape of one row.

one promptIDs [1, 4] + one row [768] → [1, 4, 768]
a batchIDs [B, T] + one row [768] → [B, T, 768]
positionspositions [T] (the numbers 0, 1, …, T−1) + one row [768] → [T, 768]

So no [B, T, 1] anywhere: the IDs never get multiplied. If you want the multiplication view, it needs one-hot rows (see "The lookup is secretly a multiplication" above): each ID becomes a row of 50,257 zeros with one 1, so the IDs turn into [B, T, 50257], and then [B, T, 50257] @ [50257, 768] = [B, T, 768] (3-D multiplication is explained below). The rule matches: 50,257 meets 50,257.

And note the position table is not looked up by the token IDs. It's looked up by the position numbers 0 to T−1, which only depend on the length T. Every row of the batch uses the same [T, 768], added onto all B rows ("How the lookup works, as math" below shows the formula, and how GPT-2's code does it).

But a table needs every row to have the same length, and our texts don't. That's where training and decoding part ways.

CorePretraining batch: pack the text, no padding

Pretraining large models generally doesn't pad. It joins all the documents into one long stream, with an end-of-text token after each document, and cuts the stream into rows of exactly T tokens. Every position holds real text, so nothing is wasted. This is called packing, and it's the standard way large models are pretrained, not a trick of one codebase:

  • GPT-3 (OpenAI): "packing multiple documents into a single sequence", with documents "delimited with a special end of text token".
  • T5 (Google): "we 'pack' multiple sequences into each entry of the batch".
  • Llama 3 (Meta): packs too, and adds "an attention mask that prevents self-attention between different documents within the same sequence" (see below).
  • GPT-2's paper doesn't say how it built its rows. nanoGPT, which reproduces GPT-2 and whose code we can read, packs: its data script appends the end-of-text token (ID 50256) after every document.

The packing is done by the data-preparation code, after tokenizing, not by the tokenizer.

CoreHow the lookup works, step by step

First, the names. wte and wpe are just what GPT-2's code calls the two tables:

wtethe token table (token embeddings): 50,257 rows, one per token ID, 768 numbers each
wpethe position table (position embeddings): 1,024 rows, one per position, 768 numbers each
idsthe token IDs from the tokenizer, shape [B, T]
xthe result, what goes into layer 1, shape [B, T, 768]

The whole step works on whole rows. For each cell of the ID table (batch row b, position t):

x[b, t]  =  wte[ ids[b, t] ]  +  wpe[ t ]

In words: copy the token table's row whose number is the ID, copy the position table's row whose number is the position, and add the two rows, number by number. Each of these is a whole row of 768 numbers. The ID only says which row to copy: its value never goes into the sum, and none of the table's numbers get multiplied.

Reading the formula: what x[b, t] picks out

x has 3 dimensions, [B, T, 768]. Writing x[b, t] gives only 2 of its 3 indices, and the ones you leave off the end are taken in full. So x[b, t] is one token's whole row, all 768 numbers:

xno index: the whole block, [B, T, 768]
x[b]1 index: one batch row, all its tokens, [T, 768]
x[b, t]2 indices: one token's row, [768]
x[b, t, d]3 indices: a single number

The rest of the formula reads the same way: ids is 2-D [B, T], so ids[b, t] is one number (the ID, like 3797); wte[3797] and wpe[t] each give one row of 768. So the formula is row = row + row, every piece [768]. You can make the third dimension visible with :, which means "all of this dimension":

x[b, t, :] = wte[ ids[b, t], : ] + wpe[ t, : ]

Exactly the same thing; the : just shows that whole rows of 768 are copied and added.

The formula is one step of a loop

The formula is what happens for one cell (b, t): one token, one row of 768 numbers. Doing it for every cell fills the [B, T, 768] block:

# every batch row b, every position t:
for b in range(B):
    for t in range(T):
        # the formula = one step
        x[b, t] = wte[ids[b, t]] + wpe[t]

For our sentence (B = 1, T = 4) that's 4 steps:

step 1
b=0, t=0		x[0, 0] = wte[464] + wpe[0]  (The)
step 2
b=0, t=1		x[0, 1] = wte[3797] + wpe[1]  (cat)
step 3
b=0, t=2		x[0, 2] = wte[3332] + wpe[2]  (sat)
step 4
b=0, t=3		x[0, 3] = wte[319] + wpe[3]  (on)

In real code you don't write that loop. You write one line, x = wte[ids] + wpe[:T], and numpy or PyTorch run the loop inside their own compiled code (C/C++ on a CPU, CUDA on a GPU). On a GPU the B × T row copies run in parallel instead of one after another. A Python loop gives the identical result but is very slow, because Python does one step at a time; the notebook has you write it once, only to see what the one-liner does. Writing a step once for all cells and letting the library loop is called vectorization, and every later episode works this way: attention, for example, handles the whole [B, T, 768] block at once with a few matrix multiplications (plus a softmax), never a Python loop over the tokens in it. (When generating text, the model is run once per new token; that loop comes in a later episode.)

So a 2-D table indexed by a 2-D table of IDs gives a 3-D result. Here's where the third dimension comes from.

1. wte[ids]: keep the layout of ids, swap each number for its row. Picture the ID table, then replace every number in it with the row of the table that has that number:

ids  [2, 2]:
[[2, 4],
 [3, 2]]

swap each ID for its row of E:
[[ E[2], E[4] ],
 [ E[3], E[2] ]]

write the rows out  [2, 2, 3]:
[[[0, 1, 4], [1, 1, 0]],
 [[3, 2, 2], [0, 1, 4]]]
  • The grid of ids, 2 × 2, stays exactly where it was: the result still has batch row b and position t.
  • Each cell, which held one number, now holds a whole row of 3. That row length is the new, third dimension: [2, 2] → [2, 2, 3]. For GPT-2 it's [B, T] → [B, T, 768].
  • Any cell of the result can be read off with one rule: wte[ids][b, t] = wte[ ids[b, t] ]. For example, the result at b = 1, t = 0 is E[ids[1, 0]] = E[3] = [3, 2, 2].

The same thing, growing the index one step at a time:

E[2]one number → one row: [0, 1, 4], shape [3]
E[[2, 4]]a list of 2 numbers → rows 2 and 4, stacked: [[0, 1, 4], [1, 1, 0]], shape [2, 3]
E[ids]a [2, 2] table of numbers → a row for every cell: shape [2, 2, 3]

The rule is always the same: the result has the shape of the index, plus the shape of one row. numpy calls indexing with a list or array of numbers "integer array indexing" (E[[2, 4]], E[ids]); PyTorch does exactly the same with its own tensors (W[ids]). There's no loop in your code, but underneath, the library does what our trace table did: for every number in ids, find that row and copy it.

2. wpe[:T]: a slice, not an ID lookup. :T means "rows 0 up to T−1". It doesn't look at the IDs at all, only at how many positions there are. With T = 2: P[:2] = rows 0 and 1 = [[0, 1, 0], [1, 0, 0]], shape [2, 3]. (Writing P[[0, 1]] or P[np.arange(T)] gives the same rows.)

3. The +: [2, 2, 3] + [2, 3]. The shapes are lined up from the right: the last two sizes, [2, 3], match, and the extra batch dimension in front is missing on the right side. So numpy (and PyTorch) adds the same [2, 3] to every batch row:

x[0] = E[ids][0] + P[:2]
     = [[0, 1, 4], [1, 1, 0]]
     + [[0, 1, 0], [1, 0, 0]]
     = [[0, 2, 4], [2, 1, 0]]

x[1] = E[ids][1] + P[:2]
     = [[3, 2, 2], [0, 1, 4]]
     + [[0, 1, 0], [1, 0, 0]]
     = [[3, 3, 2], [1, 1, 4]]

That's the whole of x = E[ids] + P[:T]: shape [2, 2, 3].

4. The same line on real GPT-2. Our sentence has ids = [[464, 3797, 3332, 319]], shape [1, 4]:

  • wte[ids] = [[ wte[464], wte[3797], wte[3332], wte[319] ]]: the 1 × 4 grid stays, each cell becomes a row of 768, so [1, 4, 768].
  • wpe[:4] = rows 0, 1, 2, 3 of the position table: [4, 768].
  • + adds those 4 position rows to the one batch row: x is [1, 4, 768], exactly what layer 1 receives.

Lookup or one-hot: two ways to get the same row

There's a second way to get a row out of a table, using multiplication instead of copying. It gives exactly the same answer, and it's worth understanding once, even though GPT-2 doesn't use it.

1. What a one-hot row is. Take a row of zeros as long as the vocabulary (5 in our toy model) and put a single 1 at the position of the ID, counting from 0. For ID 2:

ID 2  →  one-hot row [0, 0, 1, 0, 0]  (the 1 is at position 2)

2. One token: multiply the one-hot row by E. The shapes: one-hot [5] @ E [5, 3] = [3], one row. The easiest way to see what happens: each number of the one-hot row multiplies one whole row of E (the number at position 0 multiplies row 0, the one at position 1 multiplies row 1, and so on), and then the 5 products are added together:

one-hot numberrow of Eproduct
0 ×row 0 = [2, 0, 1]= [0, 0, 0]
0 ×row 1 = [1, 3, 0]= [0, 0, 0]
1 ×row 2 = [0, 1, 4]= [0, 1, 4]
0 ×row 3 = [3, 2, 2]= [0, 0, 0]
0 ×row 4 = [1, 1, 0]= [0, 0, 0]
add the 5 products= [0, 1, 4] = row 2

Every row that meets a 0 becomes all zeros. The one row that meets the 1 passes through unchanged. Adding them up leaves exactly row 2. Multiplying by a one-hot row selects a row, which is what the lookup does by copying.

The same multiplication, one number at a time (each answer number is a dot product of the one-hot row with one column of E), gives the same result. It's the same 15 multiplications, just grouped by column instead of by row:

number 00×2 + 0×1 + 1×0 + 0×3 + 0×1 = 0
number 10×0 + 0×3 + 1×1 + 0×2 + 0×1 = 1
number 20×1 + 0×0 + 1×4 + 0×2 + 0×0 = 4

3. From the ID table [B, T] to a one-hot block [B, T, 5]. Steps 1 and 2 handled one ID. For a whole table of IDs, do step 1 for every cell: each single number is replaced by a row of 5 numbers. Replacing every number with a row adds one new dimension at the end, and its size is the vocabulary:

A batch of 1, ids [[2, 4]], shape [1, 2] → one-hot block, shape [1, 2, 5]:

b=0, t=0:  ID 2 → [0, 0, 1, 0, 0]
b=0, t=1:  ID 4 → [0, 0, 0, 0, 1]

A batch of 2, ids [[2, 4], [3, 2]], shape [2, 2] → one-hot block, shape [2, 2, 5]:

b=0, t=0:  ID 2 → [0, 0, 1, 0, 0]
b=0, t=1:  ID 4 → [0, 0, 0, 0, 1]
b=1, t=0:  ID 3 → [0, 0, 0, 1, 0]
b=1, t=1:  ID 2 → [0, 0, 1, 0, 0]

GPT-2, ids [[464, 3797, 3332, 319]], shape [1, 4] → one-hot block, shape [1, 4, 50257]: 4 rows of 50,257 numbers, each with a single 1 (at positions 464, 3,797, 3,332 and 319).

Cell by cell, the rule is: start with a block of zeros of shape [B, T, V], then for every cell (b, t) put a 1 at position ids[b, t] of its row:

onehot[b, t, ids[b, t]] = 1  (everything else stays 0)

Three ways to write it in code, all giving exactly the same block:

  • A loop: onehot = np.zeros((B, T, V)), then for b … for t …: onehot[b, t, ids[b, t]] = 1 (you do this in notebook section 1.4).
  • np.eye(V)[ids]: np.eye(V) is a V × V table with 1s on the diagonal, so its row i is exactly the one-hot row for ID i. Picking its rows with ids builds the whole block. (So making one-hot rows is itself a lookup.)
  • PyTorch: torch.nn.functional.one_hot(ids, V).

✓ Checked: the loop, np.eye(5)[ids] and F.one_hot(ids, 5) give identical blocks, and for GPT-2 F.one_hot turns our [1, 4] into [1, 4, 50257].

  • Training (Episode 7): because the lookup equals a multiplication, its gradient follows the same rule as any other multiplication, and that rule says: add each position's gradient into the row it used. That's the "training through a lookup" box below.

What those functions do:

  • nn.Embedding(50257, 768) (PyTorch): a layer that holds a learned [50257, 768] table (its .weight). Calling it, self.wte(input_ids), runs PyTorch's F.embedding, which picks the rows: the same as weight[input_ids]. In PyTorch, an Embedding layer is just a table you look rows up in.

Three spellings, one operation: pick rows by their numbers. None of them builds one-hot rows.

Why not one-hot? It gives the same answer the slow way. One token costs 50,257 × 768 = 38,597,376 multiplications (each followed by an add), and all but 768 of them multiply by 0. The lookup just copies 768 numbers.

Go deeperWhat the computer actually does

In memory, the token table isn't a grid. It's one long run of 38,597,376 numbers (float32, 4 bytes each), stored row after row: all 768 numbers of row 0, then all of row 1, and so on. So row i starts at number i × 768.

A lookup is just arithmetic on that address, then a copy:

  1. Take the ID, say 3,797 (" cat").
  2. Find where its row starts: 3,797 × 768 = number 2,916,096, which is byte 11,664,384 (2,916,096 × 4).
  3. Copy the next 768 numbers (3,072 bytes). That's the row.

For our [1, 4] IDs that's 4 copies; for a batch [B, T] it's B × T copies. They don't depend on each other, so a GPU does them in parallel. None of the table's numbers gets multiplied: the only arithmetic is on the address (3,797 × 768), then it's a straight copy.

✓ Checked on real GPT-2: the table is stored this way (contiguous, step of 768 numbers from one row to the next), and the 768 numbers starting at number 2,916,096 are exactly row 3,797 (identical).

During training the lookup runs backwards: each position's gradient (its training signal, Episodes 5 to 8) is added into the row it came from. If an ID appears twice, its row gets both added together. In our padded batch the pad ID 50,256 appears twice, so with a test loss that just adds up every output number (not a real training loss, which leaves pads out; see the next section), every number in its row's gradient is 2, while for " cat", used once, it's 1.

CoreMatrix multiplication with 3 dimensions

A batch turns every table into a 3-D block like [B, T, 768], and from Episode 2 on we multiply those blocks by weight matrices. The rule is the same 2-D multiplication you already know, done once per sheet.

[B, T, K] @ [K, N] = [B, T, N]
  • Only the last dimension of the left side meets the second-to-last dimension of the right side (for a 2-D W like this one, that's simply its first). They must match (K and K) and they disappear, exactly as in 2-D.
  • The other dimensions in front (B and T) just come along. Each of the B sheets [T, K] is multiplied by the same matrix W, giving B sheets [T, N].

  1. A loop over the sheets: multiply sheet 0 by W, then sheet 1 by W, and stack the answers. The result is identical.
  2. Flatten first: put all 2 × 3 = 6 rows into one [6, 4] table, multiply by W to get [6, 2], and cut it back into 2 sheets. The result is identical. Every row is multiplied by W on its own, so it doesn't matter which sheet a row belongs to.

In numpy and PyTorch you just write X @ W; they handle the extra dimensions for you.

CoreSee 3-D multiplication in 3D

The same example, cell by cell. X is on the left, the shared W sits above the answer Y, so row i of a sheet and column j of W meet at Y[b, i, j] (sheet b). Tap through the steps.

Go deeperWhen both sides are 3-D

Sometimes both sides have a batch dimension. Then sheet b on the left is multiplied by sheet b on the right; sheets never mix. The B's must be equal, or one side has no batch dimension (or a size of 1) and is reused for every sheet, as W was above: broadcasting again. Anything else is an error.

[B, T, K] @ [B, K, M] = [B, T, M]

This exact pattern is coming in Episode 2: the raw attention scores (before a scaling step) are Q [B, T, 64] @ K-flipped [B, 64, T] = [B, T, T], one score table per row of the batch, so no row ever looks at another row's tokens. (Inside one packed training row, two documents can still see each other unless the model adds a mask for that, as Llama 3 does.) With 12 heads the blocks get a fourth dimension, [B, 12, T, 64], and the rule stays the same: the last two dimensions multiply like a 2-D matrix, and every dimension in front is just "one product per slice".

CoreThe same rule on real GPT-2

  • Our lookup as a batch: one-hot [3, 4, 50257] @ token table [50257, 768] = [3, 4, 768], identical to looking up the rows (largest difference 0.0).
  • A real weight from Episode 2: layer 1's query weights for its first attention head are a [768, 64] matrix (64 of the 2,304 columns in GPT-2's combined attention weight). Our batch [3, 4, 768] @ [768, 64] = [3, 4, 64]. (The real model first normalizes the rows and adds a bias; Episode 2.)
  • Multiplying each prompt's sheet separately gives the same numbers (largest difference 0.0). Flattening to [12, 768] first gives the same numbers up to rounding (largest difference 1.2e-06, from adding the same products in a slightly different order).

Go deeperDo models even need position rows?

Not always, which is a nice surprise. A 2022 study (Haviv et al., "Transformer Language Models without Positional Encodings Still Learn Positional Information") trained GPT-style language models (125M to 1.3B parameters) with no position information at all and found them "still competitive with standard models", though slightly worse (for example 13.10 vs 13.05 perplexity on the Pile; lower is better). The authors' explanation, a conjecture they back with probing experiments, is the causal mask, which we build in Episode 2: each token can only look backwards, so it can work out roughly how many tokens came before it.

Modern models mostly don't add a position table either. They use RoPE, which rotates numbers inside attention instead (Episode 11, and the RoPE article). GPT-2's add-a-row approach is the simplest version, which is why we start here.

CoreOur own model: TinyGPT, part 1

Everything so far took GPT-2's tables apart. Now we start our own model, TinyGPT, in PyTorch. It grows by one piece per episode: today the two tables, then attention (Episode 2), a full block (3), all the blocks and the next-word scores (4), and in the training episodes it is trained from scratch on the TinyStories data. Its weights start random.

The code is written once, and a few settings decide the size: n_layer blocks, each token's vector n_embd numbers wide, n_head attention heads, and block_size, the longest text it can read. GPT-2 small is 12 layers × 768. TinyGPT's default is 6 × 384, small enough to train on a free Colab GPU.

@dataclass
class TinyGPTConfig:
    vocab_size: int = 50257   # GPT-2's tokenizer, so we keep its 50,257 IDs
    block_size: int = 256     # longest text TinyGPT can read (positions 0..255)
    n_layer: int = 6          # blocks stacked (they arrive in Episodes 2-4)
    n_head: int = 6           # attention heads (Episode 2)
    n_embd: int = 384         # width of each token's vector

class TinyGPT(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.cfg = cfg
        self.wte = nn.Embedding(cfg.vocab_size, cfg.n_embd)   # [vocab_size, n_embd]
        self.wpe = nn.Embedding(cfg.block_size, cfg.n_embd)   # [block_size, n_embd]
        # start random, the way OpenAI's GPT-2 code does
        nn.init.normal_(self.wte.weight, mean=0.0, std=0.02)
        nn.init.normal_(self.wpe.weight, mean=0.0, std=0.01)

    def forward(self, idx):
        B, T = idx.shape                          # token IDs [B, T]
        assert T <= self.cfg.block_size
        pos = torch.arange(T, device=idx.device)  # 0, 1, ..., T-1
        x = self.wte(idx) + self.wpe(pos)         # [B, T, C] + [T, C], C = n_embd
        return x

nn.Embedding is exactly the lookup from above: a table with one row per ID, and calling it with IDs returns their rows. forward is the same line as GPT-2's: token rows plus position rows.

Is the code right? A random model can't be compared with anything, but the size is only a setting. So we build a throwaway test copy at GPT-2's exact size (768 wide, 1,024 positions), copy GPT-2's two tables into it, and feed it the same batch. Its output matches what GPT-2 sends into its first layer with a largest difference of 0.0. Then the test copy is deleted: TinyGPT keeps its own random weights. (GPT-2's tables could never go into TinyGPT itself: [50257, 768] doesn't fit into [50257, 384].)

What random means. In GPT-2's trained table the words closest to " cat" are ' Cat', ' cats', 'Cat', 'cat', ' dog', ' Cats'. In TinyGPT's random table they are ' Akin', 'annel', ' establishing', ' relics', ' hyper', '<': noise. Training is what gives the rows meaning.
